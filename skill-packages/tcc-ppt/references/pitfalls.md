### 空 pages 让校验器「集体假通过」（2026-09-24 实测，已修）

**症状**：Step 2 的 `check_json_integrity.py` / `check_required_slots.py` 双双打印，
但 Step 3 build 立刻崩 `KeyError: 'pages'`；平台自动改对后又崩
`FileNotFoundError: 模板文件不存在 '009_creative.svg'`；再改又崩
`ValueError: 009 创作页缺少 body_svg 字段` —— **三个错串行暴露、反复重跑**。

**根因**：两个校验器都写成 `pages = cfg.get('pages', [])`。
配置顶层键名写错（或整个数组漏写）时，这里**不报错、只拿到一个空列表**，
于是后面所有 `for p in pages` 的逐页检查**空转 0 次**，统统打印——
一个根因让三道检查集体失效，问题被一路放行到 build 才爆。

**修法（已落地）**：
1. `check_json_integrity.py` 新增 **② 顶层结构**：`pages` 必须存在且为非空数组 —— 假通过的总闸门
2. 同脚本新增 **⑤ 009 页 `body_svg`**：字段存在性 + 片段文件存在性（**原先没有任何校验器查它**）
3. 同脚本 **④ template** 检查加针对性提示：写 `009_creative.svg` 时提示真名是 `009_content.svg`
4. `check_required_slots.py` 同样加「pages 非空」前置检查

**教训**：**任何"查空集合就通过"的校验都是假校验**。
写校验器时先问一句「如果输入是空的，它会报错还是空转通过？」
—— `dict.get(key, [])` 这种"友好兜底"，放在**校验器**里恰恰是危险的。

**易混点**：`design_spec.md` 里把创作页叫 **`009_creative`**，但模板文件名是 **`009_content.svg`**。
写 `pipeline_config.json` 的 `template` 字段时必须用后者。

## SVG / 模板问题

| 问题 | 原因 | 解决 |
|------|------|------|
| 模板修改（如改宽度）不生效 | 某些 shape 有 `data-pptx-native-ref` 属性锁定了原生尺寸，覆盖了 SVG 的 bounds | 改为 `data-pptx-part="geometry"` 让导出器读取 SVG 实际尺寸 |
| 模板中有装饰平行四边形（渐变条） | 修改 PAGE_TITLE 框宽时容易忘记同步拉伸它 | 改框宽后同时等比缩放平行四边形 path 的 x 坐标 |

### 语义形状（semantic shape）导致 export 中断（2026-09-22 实测）

**症状**：`export_flat.py` 跑到某页就崩，报以下两种之一（**导出中断，PPTX 不生成**）：

| 报错原文 | 触发条件 |
|---------|---------|
| `Semantic shape text requires data-pptx-frame on its owner` | &lt;g data-pptx-semantic-object="shape"&gt; 内含 &lt;text&gt;，但**既无 `data-pptx-native-ref`（拿不到外部化记录）也无 `data-pptx-frame`** |
| `Semantic shape requires at most one paragraph-based text component` | 语义形状内**直接含 2 个及以上 &lt;text&gt;** |

**根因（机制）**：
- 导出时 `hydrate_native_payload_refs` 会用 `native_records[ref]` 把 `data-pptx-frame` 等属性**回填**到 &lt;g&gt; 上；
- 所以**既无 `native-ref`、又没内联 `frame` 的语义形状取不到 frame** → 必崩（2026-10-15 起 `assets/` 下已无此类形状）；
- 多 &lt;text&gt; 则违反"一个语义形状只承载一个文本主体"的约束。

**已覆盖的模板**：002（多 text）、003（多 text）、009（页头）→ 各有专属 patch
（`patch_002_toc` / `patch_002_toc_3ch` / `patch_003_toc` / `patch_009_content`），
**导出时由 `TEMPLATE_PATCH_MAP` 自动套用，无需手工干预**；`patch_001_cover` 保留但已**空转**。
> 🔄 **2026-10-15**：default 门面页语义形状已**全部内联 `data-pptx-frame`**（与 minimal / vibrant 同格式）
> ⇒ `patch_001_cover` 对**全风格空转**；`assets/` 下已不存在"取不到 frame"的语义形状。
> 🔄 同日：`patch_002_toc` / `002_toc_3ch` / `003_toc` 由**硬编码 id** 改为**条件筛**（只剥"直接含 ≥2 个 `<text>`"的形状）
> —— 原 id 名单会**跨风格误剥** minimal（id 撞号）。

**解法（若将来出现新模板报同类错）**：
1. 用 XML 解析（`xml.etree`）定位问题 &lt;g&gt;：判据 = `data-pptx-semantic-object="shape"` 且有直接子 &lt;text&gt;，
   且「无 native-ref 且无 frame」或「直接 text 数 > 1」；
2. 仿 `patch_002_toc.py` 新建 `scripts/patches/patch_XXX_yyy.py`，
   **移除这些 &lt;g&gt; 的 `data-pptx-semantic-object`**（让文字走普通 `convert_text` 路径，不再要求 frame、也不再限 1 个 text）；
3. 在 `export_flat.py` 的 `TEMPLATE_PATCH_MAP` 注册映射。

> 排查提示：`build_svgs.py` 的 XML 兼容性修复**只清理根 &lt;svg&gt; 标签**上的 `native-ref`，
> 既不加 `frame`，也不动内层 &lt;g&gt;，对这两类报错无效——需按上面的解法新建 patch。
> 另：**命名空间前缀**（`<ns0:g>`）—— 原 `default` 的 `002_toc` / `002_toc_3ch` / `003_toc` 用前缀、
> `minimal` / `vibrant` 用裸 `<g>`；**2026-10-15 已把 `default` 三个文件统一为裸 `<g>`**
> ⇒ **`assets/` 下已无 `ns0:` 残留**（构建期**不做**命名空间规范化——此前"导出阶段已规范化"的说法不成立）。
> ⇒ 脚本内正则**仍保留 `<(?:ns0:)?g` 作防御**（新导入的模板可能带前缀）。

### 字体回退：font-family 断链导致中文变微软雅黑（2026-09-24 实测）

**症状**：导出的 pptx 里，某一行（或整个门面页）字体不是黑体 —— 用户实际看到「微软雅黑」。

**根因**：SVG 的 `font-family` 是**继承**属性。一旦某个元素的**继承链断了**，导出器拿不到任何字体信息，
就给它填 **Office 默认中文字体（微软雅黑）+ 默认西文字体（Segoe UI）**。两个断链场景：

| # | 场景 | 具体原因 |
|---|------|---------|
| 1 | **注入块落在根 &lt;g&gt; 之外** | `inject_image_credits.py` 原先把来源标注**追加到片段文件末尾**，即根 &lt;g&gt; 闭合**之后** → 继承不到 `font-family` → 标注那行变 `Segoe UI / Microsoft YaHei` |
| 2 | **模板自带废弃字体** | `assets/templates/` 里原本混着【等线】（`009:7`）和【微软雅黑】（`010:13`，且 **Arial 在首位、雅黑在后** → 中文直接落雅黑）。外部稿转来的模板几乎必带这两种 |

**怎么定位（关键手法）**：**拆 pptx 查 `a:latin` / `a:ea`，别靠肉眼看渲染图**。

```python
import zipfile, re
z = zipfile.ZipFile('exports/xxx.pptx')
x = z.read('ppt/slides/slide1.xml').decode('utf-8')
# 统计字体声明
for m in re.finditer(r'<a:(latin|ea|cs)\s+typeface="([^"]*)"', x):
    print(m.group(1), m.group(2))
# 定位到具体那一行
for m in re.finditer(r'<a:r>(.*?)</a:r>', x, re.DOTALL):
    if 'Microsoft YaHei' in m.group(1):
        print(re.search(r'<a:t>([^<]*)</a:t>', m.group(1)).group(1))
```

这样能一眼看出「**哪一个 run** 用了什么字体」，直接锁定是标注行、还是某个模板元素。

**解决（已落地）**：
- `inject_image_credits.py` 改为插到**最后一个 &lt;/g&gt; 之前**（根 &lt;g&gt; 内部）；幂等逻辑不变，重跑会自动纠正旧结构。
- `assets/templates/` 5 个模板全部规范化：`黑体, sans-serif` / `"黑体", sans-serif` / `Arial, "黑体", sans-serif`
  → 统一为 **`黑体, Arial, sans-serif`**（中英混排形态，保证中文落黑体、英文落 Arial）；
  根 &lt;svg&gt; 的 `sans-serif` 保持不变；`002_toc` 的 4 处纯英文副标题 `{{TOC_ITEM_x_EN}}` 保留 `Arial, sans-serif`。
  改动由 `check_templates.py` 守着（模板一旦回滚成原版，Step 3a 会立刻报警），不留文件级备份。
- `check_creative_svg.py` 新增 `check_root_wrapped()`：**顶层渲染元素必须包在根 &lt;g&gt; 内**，否则报错。
  （加这条之前，断链的片段**照样"校验通过"** —— 只查属性（颜色/字号/坐标）的校验器，对**继承链断裂**完全不设防。）
- 新增 `scripts/validators/check_templates.py`，接入 **Step 3a**。

> **为什么模板字体要单设一道校验**：模板是**人工放置**的受保护资源，
> **换机器 / 重新拷贝 / 从原版恢复时字体改动会凭空丢失**，雅黑和等线就悄悄回来了。
> `check_templates.py` 只做**检查**、不做修复（避免"脚本改内容"这条口子），
> 模板一旦回退**立刻报警**，不必等导出后翻到某一页才发现。
> （实测：拿原版模板跑 → 报 55 处违规并精准点名 `009:7 等线`、`010:13 微软雅黑`。）

**排查提示**：以后遇到「字体不对」，先拆 pptx 查出**是哪个 run**，再决定改哪一层 ——
若是**片段里新加的元素**，多半是断链；若是**门面页整体**，多半是模板自带的废弃字体。

| 问题 | 原因 | 解决 |
|------|------|------|
| 中文 PDF 提取后**词内多出空格**（「机房」→「机 房」、「展厅」→「展 厅」），整篇读起来像被拆词 | `pdf_to_md.py` 合并折行时**硬拼一个空格**（原 `merged_content += " " + next`）。拉丁文靠空格分词、CJK 靠字形分界 —— 对中文补空格就是在**造假词** | 已修（2026-09-24）：新增 `join_wrapped_lines()`，**仅当折行两侧都是 CJK 时不补空格**；其余情况（任一侧为拉丁/数字）仍补空格，英文分词行为不变。8 组单测通过（中文+中文 / 中英混排 / 英文+英文 / 空串） |

## 联网取材（§0d）的坑与实测

> **本节是 §0d 的"反查资料"** —— 流程本体见 `step_0_extract.md` §0d；
> **执行时不必逐条读**，只在①**换主题后取材效果差** ②**想改选源策略** 时回来查。
> 这里回答的是"**为什么这么定**"，以及"**哪条路实测走不通**"。

### 为什么选源用「域名规则」而不是「主题 → 网站」清单

写成清单就**换个主题整套作废** —— 主题是**无穷的**、清单是**有限的**，这条路走不通。
正确姿势：候选站由**检索词 + 限定后缀**现场生成、由**域名特征**现场筛选 —— **规则与主题无关，不会过期**。

> **图片链路早就是这么做的**：`web_image_search.py` 的 `_HIGH_HOST` / `_LOW_HOST` 是**纯域名特征**
> （`gov.cn` 加分、`zhihu` / `baijiahao` 减分），**跟主题无关** ⇒ 所以"**搜图一直很顺**"。
> **正文侧对齐同一套思路即可**。

### 限定后缀表（可选，接在检索词后）

**后缀是「式」，不是「词」**：不改"搜什么内容"，只收窄"搜哪儿 / 搜哪一类页面"。

| 想要哪一级的源 | 限定后缀 |
|---|---|
| 官方 / 政务 | `site:gov.cn`、`官网` |
| 机构 / 学术 / 标准 | `协会 OR 学会 OR 联盟`、`国家标准` |
| 概况 / 现状 / 数据 | `概况 OR 现状 OR 数据` |
| 垂类（**可选，非必需**） | `攻略 OR 经验 OR 论坛` |

> **垂类不是必需品** —— PPT 只要概况 / 数据 / 时间线，**政务 + 新闻 + 百科 三档通常已够**；
> 要垂类就现搜现用，别为某个主题**预置**垂类站。
> **限定是可选项**：加上会收窄结果、**可能一组都搜不到** ⇒ 搜不到就**去掉后缀重搜**。
> 但前提是"该引擎认 `site:`" —— 实测**必应/360/搜狗上 `site:` 全部失效**（返回门户首页），
> 所以**当检索式用即可，别指望 `site:` 语法**。

### 搜索引擎可用性实测（2026-10-08，4 家全跑）

| 引擎 | 结果 |
|---|---|
| **必应 RSS**（`cn.bing.com/search?q=<关键词>&format=rss`） | **唯一能用** —— `text/xml` 结构化、一次命中目标站 |
| 百度网页 | **反爬**，只回 1,488 字节 |
| 必应 / 360 / 搜狗 HTML | 质量差 + `site:` 失效；360/搜狗只回自家站 |
| DuckDuckGo 代理 | 502 |

**RSS 是结构化接口、HTML 是网页** —— 这是能用/不能用的分界线。

### `--search` 的来源分级排序（`_search_tier`）

**官方 / 媒体优先、百科 / 内容站沉底**（同级内保留必应顺序）⇒ 从上往下取即可。
4 主题实测：`中国国家公园`→林草局政府网｜`敦煌莫高窟`→敦煌研究院 / 国家文物局。
**排序只降级不过滤** —— 想更严就照 §0d 的两张表再筛一遍。

### 源可用性实测记录（2026-10-08，拿本链路逐站实跑）

这是「**证据**」，不是「**清单**」—— 站名只用来印证域名判据，**别把它当成"可照搬的站点池"**。

| 域名 | 实测结果 |
|---|---|
| `www.gov.cn` / 文旅部 `www.mct.gov.cn` | 14K / 21K |
| 中国新闻网 / 澎湃 / 人民网 | 55K / 6K / 2.6K（新华网首页偏少 1.8K，可试内页） |
| `baike.so.com` ｜ `baike.baidu.com` | 6.8K ｜ 403 |
| `qyer.com`（穷游）｜ 马蜂窝 / 携程 / 去哪儿 | 10K ——**"垂类能抓"的样例，不是"旅游专用站"** ｜ SPA 壳页 |

### 为什么"搜图很顺、抓正文一堆 4xx"

两者难度差一个量级：

- **搜图**打的是**百度图片搜索的 JSON 接口**（返回纯数据）+ 图片走**百度 CDN** ⇒ 相当于对接一个 API；
- **抓正文**是**爬各家网站的 HTML** ⇒ 每家都有自己的反爬（TLS 指纹 / 验证页 / JS 渲染）。

⇒ **别拿"搜图顺"去类推"抓正文也顺"。**

### ③ 重叠检测（2026-10-10 新增，治"假换词"）

**病根**：`氢能储运` 主题实测中，模型第 2 次搜 `氢能 运输 储存` —— **看着换了词，其实只是拆开写**，
**必应返回逐条相同的 10 条**（纯白烧）。而当时**三道既有 WARN 一道都没触发**：

| 判据 | 为何没触发 |
|---|---|
| ① 通用词 | `运输` / `储存` **不在禁词表**里 |
| ② 疑似切碎 | 命中是**官媒 + 百科**（不是词典站）|
| ③ 累计次数 | 才第 2 次，**没到检查点** |

⇒ **"换个说法搜同一件事"能一路骗过前三道** —— 这是第四道的由来。

**做法**：`_search_log.txt` 除「时间/词/条数」外**再存一份结果 URL 指纹**
（`_url_fingerprint()`：剥 scheme / query / fragment / `www.` ⇒ `comac.cc/cpyzr/c919`），
下次搜索时与**上一次**比对，重合率 ≥ 0.6 即提示。

| 设计决定 | 理由 |
|---|---|
| **只比「上一次」，不比全部历史** | 多板块覆盖（复兴号 技术+检修）结果集**差异很大**，比历史会误伤 |
| **阈值 0.6** | 实测「假换词」= **1.0（逐条相同）**、「真换词」远低于 0.6 ⇒ 两边都留足余量 |
| **用 `min(len)` 做分母** | 两次条数可能不同（`--limit` 变化），用较小值更灵敏 |

**实测（全过）**：

| 测试 | 结果 |
|---|---|
| 指纹归一化 `http://www.x.cc/a/` = `https://x.cc/a?utm=1` | 相等 |
| `氢能储运` → `氢能 运输 储存` | **触发**「重复 10 条（重合 100%）」 |
| `液氢储运` → `液氢` | **不触发**（只触发②切碎）|
| `液氢` → `固态储氢` | **不触发**（真换子话题）|
| 边界 6/10 相同 | 触发（阈值正好 0.6）|
| 边界 5/10、2/10 相同 | 均不触发 |
| **旧 3 列格式**日志 | 容错（不崩、不误报）|

**本轮核心教训**：**"换了词"不等于"换了方向"** ——
判据应是「**结果**会不会是另一批网页」，不是「**查询词**长得不一样」。
更普适地说：**检测"是否在重复劳动"，要看劳动成果，而不是看输入的形式差异**。

**④ 的设计陷阱（自查时发现并避开）**：最初想判"这次结果好不好"——**不可行**：
`--search` 只回候选列表、**还没抓正文**，当下根本不知道有没有料。
⇒ **改为只数次数**（不判断结果），"料够不够"交给模型。
另一个关键发现：② 看的是"**词典站占比**"，而**氢能那次搜到的是化学教学页**（不是词典站）
⇒ ② **一次都没触发** —— 这正是必须有**跨调用** ④ 的原因（单次判据抓不住"次次都脏但脏法不同"）。

**④ 的第二个坑（用户指出后修正）——「措辞即约束」**：

| | 原措辞 | 问题 |
|---|---|---|
| 文档 | 「**强制**先评估」+「**不许无限搜下去**」 | 两句合起来读 = **配额上限** |
| 后果 | —— | **冷门主题被误杀**：模型第 4 次后本该继续换词，却**停手拿不足的料往下做** |

**用户原话**：`要是用户真的搜索了小众冷门的主题，不就什么都搜不到了吗`
**修正**：① 措辞改为「**回望检查点（不是上限，可以继续搜）**」；
② **区分两种走法** ——**0 篇可用 ⇒ 继续换词搜**；**已有 2~3 篇 ⇒ 才评估够不够**。
③ 代码注释里加**措辞纪律**：**永不写成「上限 / 停止 / 不许继续」**。

**核心教训：这机制从来就不阻断**（`_run_search` 照常 return 0）——
**是"文档把人吓住了"，不是"代码拦住了"**。
⇒ **写约束前先分清「脚本真的会拦」和「只是提醒」** ——
**把提醒写成禁令，会制造一个不存在的约束、误伤本来正确的行为**。
尤其当**模型是执行者**时：它读文档如读法律，**措辞的杀伤力 = 代码的杀伤力**。

**脚本级 WARN 的通用教训**：**能自动判的判据，一律前移到脚本**（文档只留"为什么"）。
判据越靠后，越依赖模型记忆 ⇒ 越容易不执行。

### 第四种「不可用」：反爬页（WAF）—— 2026-10-13 实测

前三种不可用形态（无正文 / 绝对下限 / 栏目壳页）都靠**字符数与占比**判。第四种把三条全绕过了。

**现象**（阿里云 WAF，`bjx.com.cn`）：`HTTP 200`、`[OK] Content: 3711 chars`、**零 WARN**，
内容是一坨混淆 JS（`aliyun_waf_aa` meta / `__webpack_modules__`）。
更糟的是它的**"正文占比"高达 99%** —— JS 里没有 Markdown 链接，所以反而比真文章更"像正文"
⇒ `_prose_ratio_warning` 放行；`prose_chars = 15,601 >= PROSE_CHARS_MAX` 又触发了
"真文章"豁免 ⇒ **模型收到的是全绿信号**，只能靠"读一眼"发现是乱码。

**标定**（同一口径对照）：

| | 总字符 | 汉字数 | 中文占比 |
|---|---|---|---|
| WAF 页 | 15,834 | **46** | **0.3%** |
| 真文章（对照）| 6,312 | 4,508 | **71.4%** |

⇒ 取 **5%** 落在两者之间（抓取件口径：WAF 页 3,709 字中 0 个汉字 = 0.0%）。

**事故链**（平台实跑，主题 `海上风电：机组大型化与深远海施工`）：

1. `海上风电` 被必应切碎（返回词典 / 地图）→ 换 `海上风电机组` 也切碎
   —— **连写加词**，当时按空格分词的 `_is_word_addition` 判不出来（两轮前已预言，此轮正中）
2. **只用了 2/6 条必应词就跳走**（剩下 4 条本可试同族实体）
3. 跑 360 探针 → 拿到 `北极星风力发电网`（bjx.com.cn）
4. `--list-links fd.bjx.com.cn` → 提出来的链接**全指向 news.bjx.com.cn**（同一个域）
5. **连抓 13 篇**，每篇都 `rc=0`，每篇都得"读一眼"才发现是乱码 ⇒ 死循环

**修法（2026-10-13，三条）**：

1. **反爬页判据** —— 正文中文占比 < 5% ⇒ `[WARN]`（`web_to_md.py` 与
   `check_research_volume.py` **同源，改一边必须同步另一边**）
2. **同域名连败熔断** —— 同一个站连续 2 篇不可用 ⇒ `[STOP]`；**第 3 次再抓同站直接拒**
   （`rc≠0`，进站前拦）。实测：原来会抓 13 篇，现在**第 3 篇就被拦住**。
3. **文档「换源」→「换域名」** —— 反爬 / 壳页是**站点级**的，换同站的另一篇没用。

**教训**：**判据的"豁免条款"是最容易被绕过的一环。** `PROSE_CHARS_MAX = 1000`（2026-10-15 起下调为 `800`，见本章末补记）的用意是
"防误伤外壳重的真文章"，却被 WAF 的 15,601 字混淆 JS 一举击穿 ⇒ **写豁免前先问：
什么坏东西也能满足它？**

### 已撤回：「好源不足」判据（2026-10-10，方向反了的负结果）

**背景**：`氢能储运` 实测 10 条里 6 条是百科/知乎/无关站（只有 2 条国家能源局），
看似该加一道"词太泛"的判据。设计为 **`_search_tier == 0`（官方/媒体）条数 < 2 ⇒ 提示**。

**回测四个历史样本 —— 方向完全反了**：

| 词 | 好源数 | 真实质量 | 判据预测 | 对错 |
|---|---|---|---|---|
| `氢能储运` | **2** | 泛（该提醒）| **不触发** | 漏报 |
| `液氢` | **0** | 真金（新能源网 15K + 艾邦 17K）| **触发** | **误伤** |
| `二十四节气` | **0** | 实测 30 分钟跑完、一次即中 | **触发** | **误伤** |
| `C919 大型客机` | **5** | 好 | 不触发 | |

⇒ **误伤两个实测最好的词、放走真正该提醒的那个。**

**根因**：`_search_tier == 0` 只认 `*.gov.cn` + 主流媒体，
**行业技术站（新能源网 / 艾邦氢能源）落在 tier 1** —— 而这**恰是 PPT 最需要的源**。
**「好源条数」衡量的不是"词好不好"，而是"这个话题有没有官方表态"** —— **两件事。**

**另一条被否掉的路**：把 ②（`_shredded_hits`）放宽到整个 `_SEARCH_LOW_HOSTS`（含百度百科/知乎）。
**也不行** —— `液氢`（最好用的词）**同样含**百科 + 知乎 ⇒ **照样误伤**。
**② 的现有设计是对的**（用"纯垃圾站"判"词被切碎"）；`氢能储运` 的病**不属于"切碎"**。

**本轮最值钱的教训**：
1. **别用"来源等级分布"去判"查询词质量"** —— 两者只是**相关**，不是**因果**。
2. **加机器判据前，必须拿历史实跑样本回测** —— 否则会造出一个**方向相反**的判据；
   本例若直接上线，会**误伤两个最成功的案例**、且**静默**（只是不报警，没人会发现）。
3. **"看起来该加"≠"加了就对"** —— 三次自我纠错（①误判旧版 ②误判该放宽 ③误判好源判据）
   全部靠**拿真实数据回测**发现。**先回测，再落笔**。

### 文档里的裸尖括号标签会被渲染器「吃掉」（2026-09-24 实测）

**现象**：查看本目录文档或 `SKILL.md` 时，**从某一行开始，往后的整段正文突然变成一张图片**（base64 内联 SVG），字读不到了。

**根因**：文档里写了**未转义的**尖括号标签。文本渲染管线会把**原始 markdown** 塞进一个 svg 容器当文本内容；解析时那个裸标签被当成**真标签**，于是把**后面所有内容都吞成它的子节点**，再整体序列化成一串 base64 图片。

> **定位手法**：某处开始「变成图片」时，用正则扫该文件里「左尖括号紧跟字母」的 token。
> 实测触发点是 `pitfalls.md:59`（那里用反引号包了 svg 标签名）。`text`、`g` 这类标签名同样有风险，
> 其中 **svg 最致命 —— 它跟渲染器的根元素同名**，一撞就整段沦陷。

**规则（写文档时遵守）**：**围栏代码块之外**，凡要提到标签名，一律写成 HTML 实体 ——
把左尖括号写成 &lt;、右尖括号写成 &gt;。渲染出来仍是标签本身的样子，但任何管线都只把它当**纯文本**。

| 写法 | 渲染出来 | 危险管线 | 结论 |
|------|---------|---------|------|
| 反引号包一个裸标签 | 标签 | 被当标签解析，**吞掉后文** | 禁用 |
| 反引号里放 HTML 实体 | 实体源码本身（§代码片段内实体不解码） | 安全 | 能跑但显示难看 |
| **直接写实体、不加反引号** | 标签 | 安全 | **推荐** |

> 关键：**实体不要放进反引号里** —— CommonMark 规定代码片段**不解码实体**，
> 会直接把实体源码原样显示出来。

**已处理（2026-09-24）**：11 个 `.md`、69 行完成转义（改动已实测验证，不留文件级备份）。
`scripts/pptx_shapes/data/NOTICE.md` **故意不动** —— 里面是 markdown 自动链接（尖括号包 URL），转义会让链接失效。

**已知残留**：围栏代码块内仍有 83 行裸标签。为了**保持可复制性**（改了就 copy 不出正确代码）

| 自研 PPTX→PNG 渲染器输出「图片空白、整体下移 120px」 | ① 只认 &lt;p:sp&gt;，**分组（grpSp）内的 &lt;p:pic&gt; 被跳过**；② 导出器把组内子元素写成**页面绝对坐标**，渲染器又叠加了一次组的 `off` → 双重偏移；③ 图片映射用 `id(lxml element)` 作 key，而 lxml 元素代理对象 id 不稳定 | 三处已修：递归收集 `picmap`（用 `getroottree().getpath()` 作稳定 key）、新增 `draw_pic` 按 slice 语义裁剪、grpSp 坐标自适应（子元素包围盒 ≈ 组 off 时不叠加）。**教训：看图下结论前，先用像素扫描验证工具的坐标系是否正确** |
| 页面里的照片在第三方工具里显示正常，在自研渲染器里空白 | 同上（渲染器缺陷，非 PPTX 问题） | 涉及导出正确性的判断，**以 PPTX 的 XML 为准**（`p:pic` 计数、`blipFill`、`a:alpha` 都可直接查），渲染图只作视觉参考 |

### 结论：浅底派生的合规性与落地（2026-09-21 实测）

- 公司 8 色表里没有浅蓝/浅灰，但**允许用色表色 + `fill-opacity` 派生浅底**（`fill-opacity` 在 `canonical_authoring_contract` 的允许属性白名单内，`check_colors` 只校验色值、不校验透明度）。
- **导出链路完整保留透明度**：`fill-opacity="0.06"` → &lt;a:srgbClr val="003C96"&gt;&lt;a:alpha val="6000"/&gt;；实测 0.04（斑马纹）、0.2/0.12（细线）、0.85（压图图注条）全部原样落地，翻页/另存不丢。
- 只能用 `fill-opacity` / `stroke-opacity`，**不要用 `opacity`**（会连带子元素一起透明）；文字一律纯色不透明。

## 版式问题

### Step 2 返工为什么这么贵 —— 2026-10-10 茶马古道实测归因

**背景**：Step 2 总耗时 **21 分 19 秒**。拆开看，**纯创作只占 28%，修错占 74%**：

| 环节 | 耗时 | 占比 |
|---|---|---|
| 写 8 个 SVG 片段（必要） | 364s | 28% |
| **修 page04/05/07/08 越界** | **402s** | **31%** |
| **修 page11/13/14 越界+密度** | **211s** | **16%** |
| **修 page07（分 3 次）** | **165s** | **12%** |
| **修 page11 密度** | 75s | 5% |
| 各轮校验（6 次） | 62s | 4% |

**三类病因，性质完全不同**：

| # | 病因 | 典型页 | 治本手段 |
|---|---|---|---|
| ① | **多栏文字越界**（模型按通栏语感写长句） | page04/05/07/08 | **先验字数表**（契约 §5.0 ②，已落地） |
| ② | **块内密度不足**（框撑大、里面空） | page11 | 见 §5.0.1（素材量问题，非排版） |
| ③ | **改错方式不对** —— "挤牙膏" + "改了没生效" | page07 | **改片段两铁律**（见下） |

**病因③ 最值得记 —— 它纯属流程浪费，与判据、与模型能力都无关**：

1. **挤牙膏**：page07 一行行分 **3 次**改（`64s + 75s + 26s`）⇒ 若一次扫全页改完，**省 165s**。
2. **改了没生效**：日志原话 —— *"page07 line 256 still has the old text. The file wasn't properly overwritten."*
   ⇒ 白烧 `12s + 75s` 才发现。**根因**：用局部替换（`sed`/正则）改多字节中文的 SVG，**写不进去且不报错**。
   **正解 = 整文件重写 + 写完回读确认**。

**⇒ 已落地的文档改动**（`step_2_pipeline_config.md`）：
- 「**落笔前宽高自查**」（省一轮）+「**一口气全写完 → 一次全量校验 → 按报错返工**」；
- 「**改片段两铁律**」：① 一次改到位别挤牙膏 ② 改完立刻回读，**"改了没变化先怀疑写入、别怀疑判据"**。

**同轮被证伪的两个"省时间"设想**（别再往回加）：

| 设想 | 为什么听着对 | 实测结论 |
|---|---|---|
| **分批写 + 中途校验** | "早发现早止损" | **净亏 342s**（写作 364s→706s），且**发现时机完全不变** —— 分 5 批里**一次中途校验都没做**，还是"全部写完才跑第一次"。**分批 = 纯损耗** |
| **单页探针**（先跑 1 页验手感） | "第一页错了后面别重犯" | **前提不成立** —— 8 页用 4+ 种骨架，`page04`（三栏 384）**不可能**犯 `page13`（通栏 1200 矮卡）那种错，**一个版式测不出另一个版式的错** ⇒ **零预测力** |

**真正防错的是「先验」不是「探针」**：把「栏宽→单行字数」「容器高→行数」在**落笔前**算足（契约 §5.0 ②），
错误根本不会写进文件，校验器只是**兜底**。**先验表让返工从 853s → 151s（−82%），跟分批与否无关。**

**通用教训**：**"返工贵"未必是判据不好 —— 先量一下钱花在哪**。
本例 74% 的返工里，有 **17% 纯属"改法不对"**（挤牙膏 + 写不进），跟判据质量毫无关系。
**优化前先归因，别默认"加判据"就是答案。**

### 左右分栏高度失衡 + 骨架高度同质（2026-09-24 实测于 SkillGo 平台真实产物）

**现象**（用户肉眼一眼看出，非脚本发现）：某 15 页 deck 里 **4/5/7/8/9/12 六页**布局几乎一样，
而且"右侧图片铺满到底、左侧空出一大截"。拆 pptx 量化后确认是**两个独立缺陷**：

| 缺陷 | 实测数据 | 性质 |
|---|---|---|
| **A. 左右分栏高度失衡** | 见下表，最大差 **228px** | 分栏收口线没对齐（§2.2b） |
| **B. 骨架高度同质** | 6 个内容页**全部**用「左文右图」 | 反重复只查"相邻不同"，被"A-B-A-B"钻空子（§2.1） |

**A 的量化证据**（画布 720，内容底边基准 648）：

| 页 | 左栏底 | 右栏底 | 差值 | 谁偏短 |
|---|---|---|---|---|
| 4 | 412 | 640 | **228** | 左（2 卡只到 412，右 2 图铺满） |
| 5 | 648 | 464 | 184 | 右（图只到 464，左有底部条到 648） |
| 7 | 412 | 556 | 144 | 左（2 卡 vs 1 张大图） |
| 8 | 648 | 548 | 100 | 右（图组只到 548） |
| 9 | 528 | 640 | 112 | 左（3 卡只到 528，右 2 图铺满） |
| 12 | 648 | 548 | 100 | 右（同 8） |

**根因**：
1. 契约 §5.1「图文左右」原文**只有一句话**（"左半 580、右半 580，两张卡叠一张图"），
   信息量过低 → 模型自由发挥时**默认2~3 张 100px 矮卡 + 一/两张铺满高图**，高度天然对不齐；
2. 契约**没有"分栏必须等高收口"这条规则** —— §2.2 只管"元素间距/重叠"，不管"两栏底边是否齐"；
3. §2.1 反重复只约束"**相邻**两页不同骨架"，**没有任何累计占比上限**，
   于是可以"A-B-A-B"隔页轮换而观感依旧雷同；
4. **图注条底边 ≠ 图片底边**：组件 C4 图注条压在图片下缘，图片框底 640 时图注条仍在图内，
   内容底边就是 **640**，容易算错。

**解决（已落地）**：
- 契约新增 **§2.2b「左右分栏高度对齐铁律」**：分栏页左右底边误差 **≤24px**；
  给出 5 种补齐手法（补正文 → 均分拉高 → 补组件 C3/C10 → 反向缩短 → 改走 §5.9 不等宽）；
  并写明"**先定右、再倒推左**"的实操顺序。
- 契约 **§5.1 扩充**：给出变体 A/B/C 的**精确坐标表**，直接套用即达标。
- 契约 **§2.1 新增第 4、5 条**：同一骨架**累计占比 ≤1/2**；Step 1 需登记每页骨架以防雷同。
  > **2026-09-29 更新**：原第 5 条要求「人工产出**骨架分布表**」，**复跑实测并未执行**（同 #23「文档要求 ≠ 模型执行」一类）
  > → 已改为 **Step 1f 机器核对**（`check_design_spec.py`）：模型只需逐页填 `**版式骨架**：§5.x` 字段，
  > 脚本自动统计「任一家族 ≤1/2」+「相邻内容页不同族」。**人工产表要求已取消。**
- `check_creative_svg.py` 新增 **`check_column_balance()`**（warning，不阻断）：
  按中轴线把元素分左/右栏（宽度 ≥1100 视为通栏、不计入），比较两栏视觉内容底边，
  差 >48px 就提示。**已用上述 4/5 两页的真实几何做样本双向实测**（能报、且合格页不误报）。

**为什么右栏要求 ≥1 个元素而不是 ≥2**：分栏页右栏常常就是"一张大图 + 图注"，
若要求 ≥2，"右图一张铺到底"这种最典型的分栏反而被漏检 —— 第一版就踩了这个坑。

**给写片段者的自检口诀**：
> 写完分栏页，先问「**左栏最后一行底边**和**右栏最后一张图/图注条底边**，是不是同一个数？」

### 表格/卡片下方元素贴太近（2026-09-22 实测）

**现象**：page02 的表格最后一行（`rect y=560`，底边 616）与下方流程链标签（`text y=616`）视觉上贴在一起，实际已**垂直重叠 14px**。

**根因**：
1. 契约给了大量**固定坐标**（组件 C4 图注 `y=616`、组件 C5 流程链 `y=632`、底部基准 `648`），
   但没说这些坐标**只在"该组件是页面最底部元素"时成立**；
2. 契约原本**没有"元素最小间距"这条规则**，于是 AI 为了满足 `y<720` 边界，把元素层层往上挤；
3. **文字基线陷阱**：&lt;text y="616"&gt; 的 616 是**基线**，字形实际占 `602~620`，所以与底边 616 的表格**重叠**。

**解决（已落地）**：
- 契约 §2.2 新增「**区块间距铁律**」：实体区块间 ≥24px、与流程链 ≥32px、与细线 ≥16px；
  装不下时按优先级处理（压行高 → 整体上移 → 牺牲流程链），禁止靠缩间距硬塞。
- 组件 C5 与 §5.3（流程链 / 时间轴）补充：流程链 y 坐标**不是固定值**，上方有内容时必须**整体平移**（线+圆点+标签一起动）。
- `check_creative_svg.py` 新增 `check_spacing()`：自动检测垂直重叠，**已能精准复现此 bug**。
  - 豁免规则：文字/色块被另一个矩形完整包住时（压图图注、卡片内文字）不报错。

**排查提示**：报错提示"元素重叠：rect@560 与 text@616"时，**别去改 616，要整体上移流程链**。

### 纯组件 C10 独占一页 → 填充率算出 0%（2026-09-24 实测，已修）

**现象**：page08 按契约 §4.8 组件 C10 的原始定义（**无浅底、无边框**，只有序号圆 + 文字）写满一页，
`check_creative_svg.py` 报 **`填充率约 0% < 25%`** —— 但组件 C10 本身没做错任何事。

**根因**：填充率**只统计 `rect` 与 `image` 的面积**，`<circle>` / `<text>` 不计入。
组件 C10 的构成恰好全是后两者 → 面积恒为 0。

**契约自身的矛盾**：§4.8 说组件 C10「更适合做页面里的**一个区块**，而非独自撑满一页」，

**解决（已落地）**：
- 契约新增 **§5.10.1「组件 C10 实体化」**：独占一页时给每个条目**补浅底卡片 + 左侧色条**，
  升格为「组件 C1 通栏卡 + 序号圆」，坐标改用 `cx=88 / x=128`（原 `cx=64 / x=104` 只用于区块场景）。
  4 条 `y=104/242/380/518`，各高 `114`、间距 `24` → 底边 `632`。
- §4.8 组件 C10 与 §5.0 速查表均加上指向 §5.10.1 的提示；`step_1_design_spec.md` 的骨架选择表同步。

**别用「纯组件 C10 + 配图」凑填充率**：分类知识类内容（如"管道分类的五个维度"）
往往**没有对应的实景照片**，硬配一张会造成**图文不符**（实测 page08 曾配深基坑图，与管道主题完全无关）。

**也别为凑条数把两个主题塞进同一条**：违反 §2.4b「并列内容不混装」
（实测 page08 初版把"连接方式"和"保冷作业"塞进第 3 条，被要求拆成 4 条）。

### 底部大面积留白：两个检查「恰好」都放行（2026-09-29 实测于 SkillGo 产物）

**现象**：平台产物 15 页里有 **4 个内容页**下半截空着 100~216px（page04 最严重：正文表格止于 `y=432`，
下方空 **216px**）—— 而 `check_creative_svg.py` **一条警告都没报**。

**根因（掉进两个检查的夹缝）**：

| 检查 | 为什么放行 |
|---|---|
| **③ 连续空白带**（`check_blank_band`） | 代码**豁免"贴顶/贴底"的留白**：空白带若延伸到 648 即判"贴底留白"。page04 的 216px 空白带**恰好触及 648** → 放行 |
| **① 填充率 ≥25%**（`check_fill`） | 表格是**连续实体**（表头 48 + 行高 56 无缝），面积 ÷ 创作区 ≈ 52% → 轻松达标 |

**契约自身的矛盾**：§2.4 一边说「避免下半截大面积留白」，一边又说「留白只允许贴顶/贴底」——

**解决（2026-09-29 已落地）**：
- 契约 §2.4 **新增指标④「纵向收口」**：内容主体最低点应落在 **`y ≥ 608`**（距底线 648 ≤40px）——

  「底部留白偏大：内容最低止于 y=X，距底线 648 还差 Npx」。
  > **2026-09-29 更新**：实测发现软警告**被模型忽略** —— 平台产物 page04 / page14 被报后
  > 模型只清硬错误就收工，底边仍停在 **520 / 508**。已**升级为分级**：底边 **<560 → 硬错误**、
  > **560~608 → 软警告**。详见契约 §2.4 指标④。
- §2.4 标题、§2.5 仲裁表、§7.2 自检清单同步（指标数 **3 → 4**）。

### 「矮页面」的根因：只有上界、没有下界（2026-09-29 查明，已补 Step 1f）

**现象**：平台产物 page04 内容 `104~520`、page14 `104~508`，下半截各空 **128 / 140px**；
其余 6 个内容页都正常收口 `104~648`。

**直接机制（一修一坏）**：page04 原本是「表格止 440 + 通栏条 592~648」→ 中间断层 **152px > 140**（硬错误）
→ 模型把通栏条**上移**到 `464~520`（间距 24）→ **硬错误清零、底边却从 648 掉到 520**；
而当时指标④ 还是软警告 → 放行。**内容不足时，指标③（断层 ≤140）与 ④（收口 ≥608）会互相顶。**

**架构根因**：**高度是"按内容算"的，不是"按可用空间分配"的**。
- **容器驱动**型骨架天然收口：多栏并列（4 栏各 `h=544`）、组件 C10 实体化（`4×118+3×24=544`）；
- **内容驱动**型随内容缩水：表格（`7×48=336`）、卡片矩阵（上 64 + 下 236）。
- 契约 §2.2b 早就有「先定右栏到 648、再倒推左栏每卡高度」的自顶向下算法，
  **但只覆盖左右分栏，没覆盖"通栏纵向堆叠"** —— 出问题的两页正是通栏堆叠。

**为什么两阶段都放行**：Step 1 的 `check_design_spec` ③ **只查上界**（≤648 / 间距 ≥24 / 左右差 ≤24），
**没有下界** ⇒ 蓝图阶段"矮页面"完全合法；Step 2 的 ④ 当时是软警告。

**解决（2026-09-29 已落地）**：
- `check_design_spec.py` ③ **新增第 4 条断言**：本页**最下框底边 ≥ 608**（<560 阻断、560~608 警告）
  —— 把这道闸门**从 Step 2 前移到 Step 1**，返工从"生成完再改"变成"蓝图阶段就改"。
- 契约新增 **§5.0.1「选完骨架先算纵向预算」**：区分容器驱动 / 内容驱动两类骨架，
  给出「撑开」优先级（撑行高/卡高 → 加一条 → 补填充件）。**2026-09-30 已收敛**：该优先级连同另外三套清单统一为一棵决策树，见本文末「四套清单并存 → 统一为一棵决策树」节。
- §2.4 收口手段补量化（表格行高 `48→56~58`、卡片按剩余空间均分）；§4.8 组件 C9 补**反向规则**
  「算出来太空时优先撑行高」（实测 7 行 × 56 即可同时满足 ③ 与 ④：表格止 496、条 592~648、间距 96）。
  - **2026-10-08 修正**：原写 `48→56~64`，**与 `check_creative_svg` 的 `MIN_BLOCK_H = 60` 互斥** ——
    **行高 ≥60 且行内只有 1 行文字 ⇒ 文字跨度 19px ÷ 60 = 31% ⇒ 判「半空的容器」硬错误**。
    上限已收为 **58**；确要 60~64 则**行内必须放 2 行文字**。权威定义见 §4.8 组件 C9 首条。
- `step_1_design_spec.md`（§1b / §1e / §1f / 报错表 / 禁止事项）、`SKILL.md`、`step_2` 同步。

**教训**：**所有"边界类"校验都要问一句"那下界呢"** —— 只拦"超出"、不拦"不足"，
等于把一半的错判成合法；而且这类问题**不报错、只让页面难看**，比报错更难发现。

**教训**：**"贴边留白豁免"这类善意例外会开出盲区** —— 加豁免时要问一句"谁能从这条缝里钻过去"。

### 「只报像素、不给字数」→ 表格文字超宽白返工 3 轮（2026-09-30 实测，已修）

**现象**：page12（斑马纹表格）第 3 列文字超宽，模型**连改 4 轮**才过（≈2:17）：
"缩短文字" → "再缩短" → "去查实际像素宽" → "狠心砍到 ≤22 字"。而正解只需**删 2 个字**。

**根因**：`check_spacing` 的「文字越界」报错只给**像素**（`该行文字宽 497px`），
而模型手上能操作的只有**字符数** —— 那个换算比（中文 1 字 ≈ 18.67px）它得自己猜，猜一次错一次。

**解决（2026-09-30，已落地）**：报错直接附**可执行字数** ——
`｜容器可用宽 480px ≈ 25 个汉字，该行文字宽 504px、超出 24px → 再删约 2 个字（或拆成两行）`

- 可用宽用**下取整**（`480px ≈ 25 字`，**不是** 26）—— 否则"建议字数"本身就超标、自相矛盾；
- 只在对方是**容器**（`rect` / `image`）时给字数建议；`text × text` 是"行距不足"、删字无用，仍走简短文案。

**换算常量实测校准（2026-09-30，用产物 pptx 反推）**：
从 8 篇 docx 那版产物里取 48 个「盒宽确实按文字算」的样本，得出**汉字实测 19.88px/字**（= 1.065em，
最小 19.82，非常集中）；**纯拉丁/数字 0.556em** —— 与脚本里 `0.55` 的取值吻合。
- 1.065em 是**转换器给文本框留的余量**，而**字形墨宽仍是 1.0em**，所以 `CH_W = 18.67`（1.0em）
  这个口径是对的：既判"是否越界"、也用来算"删几个字"，实测**按它给的建议改一次即过**。
- 中途曾想"给建议时改用 1.065em（更保守）"，实测会导致**文案自相矛盾**
  （"可用 ≈24 字"却让"删 2 字"，25 字其实已达标）——**已撤回**，全程只用 `CH_W` 单一基准。

**教训**：报错里的**数值口径**必须和**模型能操作的单位**对齐 ——
给 px、却要它改字数，中间隔了一次它无法可靠完成的换算（同 §7.2「禁止目测判断」）。

## 「撑开手段四套清单并存」→ 统一为一棵决策树（2026-09-30）

**现象**：同一套"页面铺不满怎么补"的办法，在**四份清单**里各写了一遍，顺序互不相同 ——

| 清单 | 位置 | 档数 | 顺序 |
|---|---|---|---|
| A | ①册 §2.2b《补齐手法》 | 5 | 均分拉高卡 → 补组件 → 补正文 → 反向缩短 → 改判骨架 |
| B | ①册 §2.4《收口手段》 | 4 | 加量 → 撑行高/卡高 → 加配图 → 通栏条 |
| C | ①册 §2.4《填充不足怎么办》 | 4 | 补文本 → 加配图 → 加图形化元素 → 加说明条 |
| D | ③册 §5.0.1《撑开优先级》 | 4 | 撑行高/卡高 → 加一条 → 补填充件 → 换骨架 |

**两个后果**：① **A 表与自身文字矛盾**（编号把「补正文」排第 3，同表却写"这是最优解、优先于 1、2"）；
② **模型读到哪一套就用哪一套** —— 同一页在不同轮次可能拿到互相矛盾的顺序。

**更深的发现：「半空容器」是既有全部指标的盲区**（实测产物 page05）——
`4 栏并列 × 每栏只有 1 块 × 被撑到 544 高`，块内文字只占 202px（**密度 36%**），观感是"通高的空框"；
而它 **底边 648（④ 合规）、大 rect 占面积（① 填充率达标）、无断层、无重叠 ⇒ 所有机器检查全过**。
原因：**填充率统计的是面积** —— 一个被撑大的 rect 直接占满，机器看不出里面是空的。

**术语撞车**：同一个「层」字被用于两个概念（**结构**：上下堆叠几个块 / **流程**：第几步）
⇒ 定名为「**纵向块数**」与「**第 N 步**」。

**解决（2026-09-30 全部落地）**：
- **③册 §5.0.1 重写为唯一权威决策树**：禁止整体下移（铁律）→ 分栏先对齐 →
  主流程三步（撑块 → **缩块 + 加异质新组件** → 换骨架）。
  **第 2 步措辞修正（2026-09-30 用户提出）**：原写"加块 / 拆块"会诱导模型**复制同构空块**（页面单调），
  改为**首选「缩小原块 + 加异质新组件」、拆块降为次选**；并写明两条硬约束 ——
  ① **只加组件不缩原块无效**（密度只跟块高/内容量有关，实测 202÷544 加通栏条后仍是 37%）；
  ② **禁止为填高度复制同构空块**。
- **第 1 步"撑块"的两个条件**：① 前置校验**密度 ≥50%**；② 启用条件**该列纵向块数 ≥2**
  （**只有 1 块时一律不许撑** —— 撑完必然是"通高的空框"）。
- **两个新判据机器化**：
  · `check_design_spec.py` ⑤ **内容跨度 ≥504**（防"整体下移"：底边达标但留白搬到顶部、翻页时顶部跳动）
  · `check_design_spec.py` ⑥ + `check_creative_svg.py` G **块内密度 ≥50%**（防"半空容器"）
  · 蓝图新增字段 `**内容高度**`（与「布局框」**一一对应**；估算口径：标题 43px + 正文行 26px）
- 其余清单**压成指针**：§2.2b 只留分栏独有的「反向缩短」与「降齐」；§2.4 两处、`step_1` 两处、`step_2` 一处均改为指向 §5.0.1。
- **密度阻断线改为"前紧后松"（2026-09-30）**：Step 1f 由 **0.40 → 0.45**、Step 2 保持 **0.40**。
  依据：15 页平台产物 p7/p8 的**第二排 3 张卡 `384×320`、文字仅 ~135px ⇒ 密度 ≈42%**，
  落在 Step 2 的软警告带（40~50%）里被放行，而卡内实际空着 170px+、观感明显半空。
  判断依据是**返工成本不对称**：蓝图阶段改数字**极低**（适合卡严）／SVG 阶段改布局**昂贵**（只兜底明显不合格）。

**阈值标定**（用产物实测；原依据报告已随 `files/` 停用清理，数据保留如下）：

| 页 | 密度 | 判定 |
|---|---|---|
| page05 | **37%** | 反例 |
| page10 | 63% | |
| page08 | 71% | |

**教训**：
1. **一个规则被写成多处，就要预期它会打架** —— 而且**没有任何机器检查能发现"文档之间不一致"**。
   收敛为"**单点定义 + 其余指针**"是唯一可靠做法。
2. **加指标时要问"它统计的量能不能被人为做满"** —— 填充率统计面积，于是"把框撑大"就能骗过它。
3. `print` 文案里**不能有 markdown 加粗**（会原样打印星号）；改完文案应跑一次 **AST 扫描**，
   而不是肉眼看 —— 这已是同类问题第 3 次。

## 判据互斥导致死循环：「密度 × 跨度」在块数 = 1 时无解（2026-09-30）

### 现象
平台用最新版跑 18 页，模型在 **§2c-2 正文校验**阶段反复改写 page05 / page14，
**连续 6 轮**（38 轮 / 60 个工具操作）都在报同一条，始终出不来。

### 是「新引入」还是「历史遗留」：**病灶是历史的，触发是当天新增判据引入的**

被问过这个问题，故明确记录——**别再把本条当成"一直就有的老毛病"**：

| 层面 | 判定 | 依据 |
|---|---|---|
| **触发** | **2026-09-30 当天新增的判据引入** | 死循环的"报错方"之一是 `check_block_density`（密度 ≥50%）——**该判据是当天才加的**。平台日志原文 `39% < 40%（DENSITY_HARD）⇒ 硬错误`，正是新判据第一次生效 |
| **病灶** | **历史遗留** | 「单块列怎么排」这个场景**一直没被规则覆盖**：收口铁律（底边 ≥608）早就存在，但没有任何判据或文档处理"某一列纵向只有 1 块"的情形 |

**因果链**：
```
当天新增 check_block_density（本意：治"半空容器"静默通过）
   ↓
新判据的"分母 = 框高"碰上既有的"收口 ⇒ 必须撑满 544"
   ↓
块数 = 1 时两条判据数学上互斥（缺口 382.7px）  ⇒ 死循环
```

**两点关键澄清**：
1. **不是新判据写错了** —— 它治的问题（半空容器静默通过）是真实存在的，方向对。
   错的是**它没按「块数」分档**（见教训 5），撞上了一条它没考虑到的既有铁律。
2. **修法印证了这个判断** —— 修复**没有改任何一条老判据**，而是：① 让**新判据**在块数=1 时降级；
   ② **新增**一条前置判据（内容量下限）去治真正的病根。**动的是新加的，不是老的**。

> **当时的实跑报告（`平台实跑日志分析③`，12:33）把这次定性为"预期内的返工上升"** ——
> 它只看到 Step 2c 返工 6:14、归因为"新规则把静默缺陷变成显式返工 + 素材量偏薄"，
> **没识别出"连续 6 轮同一条出不来"是规则自相矛盾**。两小时后（14:32）才发现。
> **教训**：**"返工变多"和"卡死出不来"是两种病** —— 前者是判据变严的正常代价，
> 后者是规则互斥。日志分析别只看"返工时长"，要**核对"同一报错重复出现的轮数"**：
> 同一页同一报错 **≥3 轮**基本就是互斥，不是"模型没改好"。

### 根因：**两条铁律数学上互斥**，不是模型不听话

单块列（该列纵向只有 1 个容器）为达成收口必须把这块撑满整列 `544`；
而**"框高"正是密度的分母** ⇒ 分母拉满、分子不变 ⇒ 密度必然最低。

实测 1 标题 + 2 行正文（组件 C1：卡宽 580、正文 `x=64`，每行最多 29 字）：

| 卡内内容 | 文字跨度 | 撑到 544 时密度 |
|---|---|---|
| 1 标题 + 2 行正文 | **80.7px** | **15%** |
| 1 标题 + 3 行正文 | 104.7px | **19%** |

- 密度要 ≥50% ⇒ 框高须 **≤161px**
- 收口要底边 ≥608 ⇒ 框高须 **=544px**
- **缺口 382.7px —— 怎么改都至少违反一条。**

⇒ 模型只能在两条报错之间来回，**这是规则自相矛盾**。

### 三个具体缺陷
**① 报错文案指了一条死路**：密度报错说"走第 2 步缩小原块"，但模型**已经在缩了**（它就是缩完才触发的）。
文案没给"第 2 步也不管用"的出口。

**② 密度判据混淆「块数少」与「内容空」**：判据是 `文字跨度 ÷ 框高`。实测**同样文字量**，
做成 1 张 `h=448` 大卡 = 18%（不合格），拆成上下 2 块 = 38%（也报）。
判据实际在惩罚"块数少"，却表述为"里面是空的" —— **归因错了，修复方向自然也指错**。

**③ 缺少「内容量下限」这条前置判据**：Step 1f 原有 6 条**全是几何自洽性**（框对不对得上），
**没有一条查"这页素材够不够铺满 544"** ⇒ 模型被迫用**几何手段（撑框）**去解决**内容不足**问题,
**方向从一开始就错**，死循环只是这个错配的必然表现。

### 解决（2026-09-30 全部落地）
1. **密度判据在「块数 = 1」时一律降为软警告**（`check_creative_svg.check_block_density` +
   `check_design_spec` ⑥）—— 判据在此情形**不适用**（撑高是达成收口的唯一途径，
   低密度是素材不足的**必然结果**）。报错文案改为**劝止"再缩块"**并指向"换骨架 / 匀内容"。
   **为什么选"完全降级"而不是加"是否跨越整列"的几何判定**：新几何条件**本身就可能失准**
   （多栏 / 表格 / 半栏卡都要重新定界），我们已经吃过一次"判据自己引入新盲区"的亏。
   **能靠放宽解决的，绝不用新几何条件解决。**
2. **新增判据 ⑦「内容量下限」**（`check_design_spec`，Step 1）：
   `Σ(各框「内容高度」) + Σ(框间净距) ≥ 454` —— 抓"素材量不足以铺满本页"。
   · 用**蓝图已有的两个字段**算出，**不增加模型计算量**。
   · 阈值 **454 = 504 × 0.9**：因「内容高度」是模型**估算值**（必然偏保守），
     直接卡 504 会大量假报警 —— **假报警比漏报更糟**（会让模型开始忽略判据）。
     454 与既有 `SPAN_HARD(464)` 口径接近，避免两处判据打架。
   · **单框页整条跳过**：单框有内边距，"内容高度"表达不了配比（实测单框装 300px 内容仍误报）。
     那种页交给**密度判据**（而密度在块数=1 时已降为警告）⇒ 两者口径一致，不会互顶。
     **本条只服务多框页** —— 那才是"框间有洞、需要凑高度"的场景。
   · 报错文案给**三条可执行出路**：① 匀内容（优先）② 换矮骨架 ③ 补素材；
     并明确 **劝止"撑大框"**（会触发密度报警、两条互顶）。
3. **契约 §5.0.1「第 3 步换骨架」补直接触发条件**：**该列纵向块数 = 1** ⇒ 直接进第 3 步。
   **为什么写在第 3 步而不是第 2 步**：第 2 步正文是**"照着做"**模式（模型在执行，不在审条件），
   写在那里的"例外"最容易被跳过；第 3 步的触发条件本来就是"前面都不行才用"，
   模型决定"要不要换骨架"时**必然会读到**。符合"**铁律要放在必然会读到的位置**"。
4. 契约 / `step_1` / `step_2` / `design_spec_reference` 四处报错表同步。

### 教训
4. **加判据时必须问"它和已有判据会不会互斥"** —— 互斥的判据会让模型**在两条报错间无限循环**，
   比"漏报"严重得多（漏报只是少抓一个问题，互斥是**任务无法完成**）。
   判据越多，越要做"**两两相容性检查**"。
5. **「块数」要被当成一等公民** —— 同一个判据，块数 ≥2 和 =1 时的"正确处置"完全相反
   （撑块 vs 换骨架）。判据设计时**必须按块数分档**，否则必然误伤其中一档。
6. **"必然结果"不该被当成"失误"来报** —— 单块列的低密度是"为收口必须撑"的必然结果，
   用几何判据（密度）去卡它属于**用错工具**。**当一个报错的成因是另一条规则的必然产物时，
   应改那条规则的出口，而不是加严本判据。**
7. **新判据落地后，必须把"新判据 × 每条老铁律"过一遍** —— 本条就是新判据（密度）撞老铁律（收口）的产物。
   做这条自检时**特别关注"新判据的分母/边界"**：密度用"框高"做分母，而"框高"恰恰是收口判据的**自变量**
   ⇒ 两根判据**共用一个变量**时，方向相反就会互斥。**共同变量 = 高危信号。**
8. **排查"是不是我这次改坏的"，看"报错的判据是谁"** —— 若报错来自**新增**判据，基本可判定为"新引入"
   （哪怕它治的病是老的）；若报错来自老判据且以前就有，才是历史遗留。
   **别因为"病因是老问题"就否认"是我改出来的"** —— 老病灶可以在原地潜伏很久，新增判据只是把它**点着**。
9. **"返工变多" ≠ "卡死"** —— 日志分析时，**"同一页同一报错重复轮数 ≥3"** 才是互斥的判据；
   只看"总返工时长"会把**死循环**误读成"判据变严的正常代价"（本条当时就是这么被漏掉两小时的）。

  封面另有 `001_cover.svg` 的 `{{AUTHOR}}` 占位符。
- **原规则只说"和 .docx 文件名中的作者一致"，没说"取不到怎么办"** ——
  同事的素材文件名里没有 `-XXX` 后缀 ⇒ **规则落空**。
- 落空时模型的"就近取材"来源是**它刚读过的 skill 文档**（`step_5_export.md` 的示例文件名里写着真实人名、
  `step_0_extract.md` 的预期输出示例里也是）⇒ **把示例里的名字当成了默认值**。
- 这是 **"示例即契约"的副作用**：文档里用真实人名做示例，模型会把它当**默认值**用。

### 修法（2026-09-30 已落地）
1. **给明确 fallback**：`_meta.author` 取值优先级 = ① 素材文件名 → ② `文本.md` 正文署名 → ③ **填占位语 `TCC`**；
   `001_cover.svg` 的 `AUTHOR`（≤5字）同口径填 **`TCC`**（全大写 ASCII ⇒ 自动落 Arial，不走黑体拉丁字形）。并在 2h 收尾**主动告知调用方**"素材未提供署名"。
2. **加硬禁止**：**素材无署名时绝不编造人名，绝不填 skill 作者名**（skill 作者与用户素材毫无关系）。
3. **示例去人称化**：`step_0_extract.md`、`step_5_export.md` 里的真实人名 → **`张三`**；
   `step_2` 的示例本就用 `示例作者`。
4. 同步 6 处：`design_spec_reference.md`（§I 新增 `Author` 行 + 红线）、`step_1`（§1c + `AUTHOR` 行）、
   `step_2` §2b、`assets/templates/<风格名>/pipeline_config.schema.json`（`_meta.author` + `AUTHOR` 两处 desc）、`assets/templates/<风格名>/template_capacity.md`。

### 教训
7. **凡是"从素材取值"的字段，都必须写清"取不到怎么办"** —— 只写"和 X 一致"而不写 fallback，
   规则一落空模型就会**从上下文里就近取材**（而最"近"的上下文往往就是 skill 自己的文档）。
   **"取值来源"与"缺省值"必须成对出现。**
8. **文档示例里的人名/单位名要中性化** —— 示例是模型理解"期望格式"的最强信号之一；
   用真实人名做示例 = **把它变成一个隐式默认值**。作者信息这类字段，示例一律用 `张三` / `示例作者`。
9. **通用工具要自查"作者身份"边界** —— 本 skill 会被**别人**用于**他们自己**的素材；
   任何把 **skill 作者/作者单位**写进产物的路径都是**越界**。新增字段时问一句：
   "这个值在'素材没提供'时会落到谁身上？"

## 「示例值默认化」全库排查与修复（2026-09-30 第二轮，已修）

上一节修掉的是**作者名**一条链。追问"**还有没有同类？**"后全库排查，发现**同一条 bug 在另外 4 个位置复现**。

### 通用机制（比单个字段更重要）

> **模型把示例同时读成「格式模板」和「隐式默认值」。示例里写什么具体值，等价于给那个字段设了默认值。**

所以判定某处是否有风险，**不看"示例里有没有具体值"，而看"该示例值所在段落有没有交代这个值从哪来"**：

| 情况 | 后果 |
|---|---|
| 段落交代了来源（如"取自 §IX"） | 模型有据可依，不会编 |
| 段落**只给格式/上限、不给来源** | 规则落空 ⇒ 模型照抄示例值 |
| 示例值还恰好是**领域化真实文案** | 换领域素材时，模型顺着示例漂移 |

### 本轮修掉 4 处（A 类）

### 教训

10. **「示例即契约」要按字段逐个自查，修一条链不等于修完** —— 作者名、项目名、页面标题、

13. **必填槽位 ⊃ 素材必有能力** —— 但凡"模板必填、素材里没有"的字段（如 `_EN` 系列），
    它**必定由模型生成** ⇒ 必须为它写明**生成依据**（"是 X 的翻译"），否则"必填 + 无依据 = 自由创作"。

## 校验器盲区：图标（2026-10-12 实测查明 + 已补判据）

### 现象：两种错法**全部静默通过**，零警告

| 错法 | 当时的校验结果 |
|---|---|
| **尺寸写错**（图标 `52` 配 190 高格 ⇒ 圆底溢出格顶）| `embed_icons` **`[OK]` exit 0**；`check_creative_svg` 也不查 |
| **§VI 填 `None` 却按组件 R5 排版**（圆底上没有 `<use>`）| `check_creative_svg` **`✅ 全部通过` / exit 0 / 零警告** |

第二条实测：按组件 R5 的规格造 4 个格（`circle r=36 fill-opacity=0.08` + 标签 + 2 行短注，
**全部不带 `<use>`**）⇒ 校验全绿，**但渲染出来是 4 个空圆圈**。

### 为什么之前的判据一条都抓不住

| 既有判据 | 为什么照样过 |
|---|---|
| 填充率 ≥25% | 靠格底的浅底 `rect`（`282×190` ×4）就够，`circle` 本来就不计 |
| 块内密度 ≥50% | 判的是**文字**墨迹跨度 ÷ 框高（`101 ÷ 190 = 53%`），与有没有图标无关 |
| 竖向下界 / 跨度 | 格 `190` + 下通栏卡 `330` ⇒ 底边 648 |
| 字号 / 配色 / 坐标 | 全合规 |

⇒ **判据查的都是"可量化的几何量"，而「这个格子该有个图标」不是几何量** ——
**没有判据覆盖的那一维，写错了没人管**。

而且**没有任何脚本读 `design_spec.md` 的 §VI**（全库 grep 无命中）⇒
**不存在「§VI ↔ 正文 `<use>`」的交叉检查**。
`SKILL.md` 的逻辑是「**只有 §VI 填 `None` 才跳过图标流程**」——
于是"填了 None 却按 O 排版"**不产生任何报错**，一路全绿到出片。

| Step 2c-2 | `icon_sync.py` | 库名不在 4 风格库 / 名不存在 / 混库 / 格式不带斜杠 | `[ERROR] unsupported bundled icon library`；`[MISSING]` ⇒ `return 1` |

`embed_icons` 的 `try` **包住整个文件循环** ⇒ **一个图标写错 = 整步 finalize 停摆**（不是跳过那一页）。

### 修法：`check_creative_svg.py` 新增「图标三查」（2026-10-12，全部硬错误）

```python
ICON_SIZE_RANGE = (24.0, 28.0)      # 卡片小标题前 / 流程链节点
ICON_SIZE_EXTRA = (36.0, 44.0)      # 36 = 组件 R5；44 = 组件 C10 序号位（替代 r=22 圆）
ICON_DISC_MIN_R = 24.0              # 「浅色圆底」判定下限
```

| # | 判据 | 抓什么 |
|---|---|---|
| ① | `<use>` **必须带 `data-icon="库/名"`** | 写成 `href`/`xlink:href` **不会报错，但成稿时图标会缺**（`embed_icons` 只展开 `data-icon`）|
| ② | **边长只允许 `24~28` / `36` / `44`**，且 `width == height` | 尺寸乱写（如 O 写成 `52` ⇒ 溢出格顶）|
| ③ | **浅色圆底（`circle` + `fill-opacity` + 无 `stroke` + `r ≥ 24`）上必须压着图标** | 组件 R5 的「空圆圈」——§VI 填 `None` 时的典型症状 |

**「浅色圆底」的判定是实测标定的**：真实产物的 9 个 `circle` 里**只有 page13 的 4 个符合**；
其余全是**实心**（流程链节点 `r=8`／分隔点 `r=4`／组件 C10 序号圆 `r=22` 实心／
组件 R3 的 VS 圆 `r=36` 实心／§5.19 中心圆 `r=70` 实心）⇒ **零误伤**。

### 验证（都实跑过）

| 用例 | 结果 |
|---|---|
| **回归**：9 个真实正文片段 | **全绿、零误报** |
| 反例 1：删掉全部 `<use>`（空圆圈）| 4 条错（每个圆底一条）|
| 反例 2：`width/height=52` | 4 条「图标尺寸违规」|
| 反例 3：用 `href` 代替 `data-icon` | 8 条（4 条写法 + 4 条空圆圈）|
| 反例 4：`width=42 height=30` | 8 条（4 条非正方 + 4 条尺寸违规）|

### 教训

1. **「漏了不报错」比「报错」危险得多**。能被拦的错都在**明确的报错**里；
   真正该担心的是**没有判据覆盖的那一维**。
2. **判据只查"几何量"是不够的** —— 一个页面可以几何上完全合规、
   却缺掉一个**语义上必需**的元素（图标、图注、序号……）。
   ⇒ 补判据时要问的是「**这一维有没有机器判据**」，而不是「这条规则写清楚了吗」。
3. **凡是"某个开关关掉 ⇒ 某个组件必须换掉"的约束，都该有判据** ——
   否则"关了开关却照旧排版"就是静默失败（本例：§VI=`None` × 组件 R5）。

## 组件「选了却没人告诉你」—— ③ 册只有骨架、没有组件入口（2026-10-12 补）

### 现象

`contract_layout.md` §5.0「骨架选择速查」原本**只有"内容 → 骨架"三列，一个组件编号都没有**；
正向的组件导航只存在于 `step_1_design_spec.md` §1b（Step 1 的文档里）。
⇒ ③ 册内**只剩一张反向查询表**（§5.0「骨架 × 组件 兼容表」）：
**必须先选定骨架，才查得到能配什么组件**。
而**整页型 L1~L3 / R3~R6 根本不套骨架**（一个组件就撑满整页）⇒ **反向表对它们就是死路** ——
新组件因此长期"在 ②册定义了，却永远轮不到"（同日审计：R1~R6 曾在 ③ 册零引用）。

### 修法（§5.0 两处增改，2026-10-12）

| 改动 | 内容 |
|---|---|
| **表 1 加列** | 「骨架选择速查」新增第四列 **「可搭组件（②册 §4.8）」** —— 选骨架时顺带看到能配哪些 R1~R6 |
| **表 1 加行** | 补「**占比 / 完成度 / 构成**」一行 —— 原来 R1 / R2 没有任何正向入口 |
| **新增表 2** | 「**整页级版式速查**」7 行（L1 / L2 / L3 / R3 / R4 / R5·B / R6）：`手上的内容 → 整页组件 → 「版式骨架」字段写什么`，**跳过"选骨架"这一步** |
| **补指向** | 兼容表「七个整页级组件」处注明"什么时候该用见上方速查表，**同源**"；`step_1` §1b 指引行同步补「**＋可搭组件**；整页级另有专表」|

### 教训

**「从内容出发的正向入口」与「从骨架出发的反向查询」是两件事。**
只做后者时，模型必须先选中一个骨架，才可能摸到新组件；
**当某类组件本身不依附骨架（整页型）时，反向表结构性地到达不了它们** ——
⇒ **入口要按"素材长什么样"来建，不能只按"页面怎么分块"来建。**


## 「通道」被理解成「换词批次」—— 硬闸失效的真实机制（2026-10-12 查明）

### 现象

§0d 规定「每条通道最多试 2 条词」。实测（中国新能源汽车）**在通道 1 连试 14 条词**：
`新能源汽车` → `新能源汽车 十年 发展` → `中国新能源汽车 突围` → `比亚迪 发展历程` → … → `新能源 汽车 智能化`。

### 根因：不是"不听话"，是**概念没对齐**

日志里模型写着「Per §0d rules, I need to switch channels. **Let me try the 360 search channel**」，
紧接着执行的却是 `web_to_md.py --search 电动车 十年 弯道超车` —— **换的是词，通道一次没换**。

三条通道的**调用形式明明完全不同**（`--search` ／ `--list-links` ／ `so.com`），
但模型把「通道」读成了「搜索词的批次」⇒ **它以为自己在守规则**。

**教训**：**"重复违规"里藏着的往往是"概念没对齐"，而不是"故意不遵守"** ——
排查这类失效，先问「**它以为它在做什么**」，再问「它为什么不照做」。

### 代价

硬闸不阻断 ⇒ 不报错，但烧时间：素材准备里约 **7 分 45 秒**花在「失败 → 重新决策」，
而纯脚本执行只占 **40 秒**。

### 修法（2026-10-12）

1. **给出「换通道长什么样」的对照** —— 明确「只改 `--search` 引号里的词，你仍在通道 1」。
2. **给一个可靠的计数锚点** ——**每次 `--search` 前先显式写出「通道 1 已试 N 条」**；
   跨轮次计数对模型不可靠，**必须写下来**（这是"把判据前移到文字"能生效的形式）。
3. **没动脚本层硬闸** —— 它在 10-10 被回退过（`SEARCH_TOTAL_GATE`），动它要单独评估。

### 二次重演：文字判据也没挡住（2026-10-13）

**同一事故第二次发生** —— 2026-10-13 平台实测（主题「中国新能源汽车的十年突围」）：
三通道全部试完后，模型**又回流到通道 1**，继续换 4 条词 + 连写 8 个 Python 脚本解析 360 重定向，
**18 轮工具操作、约 12 分钟、零交付**（末轮仍在死循环）。

当天文档里写着三条硬判据，**全部失效**：

| 文档当时写的 | 实测发生 |
|---|---|
| 「每次 `--search` 前先显式写出「通道 1 已试 N 条」」| 它写了，而且**写错** —— 漏算了 `比亚迪 新能源汽车` 那条 |
| 「三通道全试完 ⇒ 终止并说明」| 没终止，回流通道 1 接着换词 |
| 「不要写 Python 解析重定向 URL（实测白烧 3 分半）」| **原样重犯**，这次连试 8 轮 |

⇒ **10-12 的结论是"把判据前移到文字"，10-13 证明文字同样挡不住。** **该硬停就得硬停。**

### 修法（2026-10-13）：预算下沉到脚本

1. **`web_to_md.py` 内置每任务预算账本**（`.runtime/channel_budget.json`，跨进程持久 ——
   每次工具调用都是新进程，内存计数器等于没有）：`--search` 6 条词 / `--list-links` 3 个 URL，
   **超限直接 `rc=2` + `[STOP]`，一个字都不搜**；每次调用先打 `[Budget] 已用 N/上限`，模型不用自己数。
2. **跨调用的换词重叠检测**：账本记 `last_keyword`，下一条词与它字符 Jaccard ≥ 0.6 ⇒ 打
   `[WARN] 重叠 N%`（模型习惯"一次只传一个词"，只比同一次调用内部的词等于没比）。
3. **通道结构解循环**：旧顺序把 360 排在栏目页之后，而"怎么找栏目页 URL"的答案又写在 360 里 ⇒ 闭环。
   改为 **必应（6 条词，主战场）→ 栏目页（3 个，入口优先取必应结果里的真实 URL）→
   360 探针（1 次，不计入通道序位，只找栏目页入口）**。
4. **删掉过期背书**：旧文档写 `so.com/link?m=…`「直接抓就行、上一轮成功」，沙箱实测**一律 400** ⇒
   改为「只取标题、别碰它的链接；看到 400 就放掉这条通道」。
5. **`reset_project.py` 同步清 `.runtime/`** —— 否则上一轮花掉的预算会带到下一轮，一开跑就被拒。

⚠️ 已知退化：skill 根只读时预算写不进去，脚本会打 WARN 并**退化成"无闸"**（宁可放过，不误拦）。

### 勿重蹈

**软提醒（"注意不要循环搜索"）对模型无效** —— 10-10 实测导致 `出国旅行` 连搜 42 次、任务取消。
⇒ **能靠"写下来的自查"解决的优先用它；解决不了的，才考虑脚本层阻断。**
（10-13 补：**"写下来的自查"也失效了** ⇒ 计数与终止类判据**一律下沉脚本**。）

## 取材阶段缺「够不够」的正向量尺（2026-10-12 补）

### 现象

§0d 只有**负向**停止判据（「连续 2 次无新增可用料」）。当**每次抓取都有新增**时它**永不触发** ⇒
模型一路「I need more content」抓下去。实测：抓到**第 4 篇时材料已够**（§0e 最终 116%），
却一路抓到 6 篇 —— 多出的决策轮次每次 26~46 秒。

### 修法

新增 `scripts/validators/check_research_volume.py`（**只读，不写任何文件**）：
扫 `_research/*.md`，逐篇算**净正文** + 判壳页，直接给「够了 /还差多少」。

- 判据来源：**两次实测反推，不是理论值** —— 大运河 3 篇 → 提炼后 2,032 字符；
  新能源 6 篇 → 1,856 字符 ⇒ **净正文 ≥ 5,000 字符 且 可用 ≥ 3 篇**。
- **抓取件 → 提炼后有明显压缩**（实测国家铁路局那篇：原文 12,698 → 净正文 2,787，约 **0.22**）
  ⇒ **别拿原文总字符去比 1600 的目标**。
- 🔄 **2026-10-14 修正：目标线不该同时当放行线** —— 实测抓取件净正文 54,472 字符、提炼后
  1,385（期望的 87%），模型为补这 215 字符重写整份 `facts.txt`，多花约 6 分钟才走完。
  ⇒ 期望 × **80%** 即放行（`emit_facts.BODY_WARN_RATIO` / `verify_extraction.TEXT_ADEQUACY_THRESHOLD`
  / `check_materials.TEXT_SUFFICIENT_RATIO` 三处同源），并把「压得太狠」在 `emit_facts.py`
  落盘时用**「条数 · 平均字符/条」**直接暴露，第一次就写足。
- 壳页判据与 `web_to_md.py` 的 `_prose_ratio_warning` **同源**；目标口径与
  `verify_extraction.py` 的 `TEXT_PER_PAGE` **同源**（避免再添一处真相）。
- 用法：抓够 **3~4 篇**跑第一次，此后每补 1 篇跑一次；见「够了」立刻进 D 段。

### 教训

**只有"失败才停"的判据是不够的** —— 还要有「**达标就停**」的正向量尺；
否则在"每次都有小进展"的场景里，模型永远收不了手。


## 自定义脚本复用判据时「预处理不同」⇒ 边界样本翻面（2026-10-12 实测）

### 现象

`check_research_volume.py` 的壳页判定**本意**是与 `web_to_md._prose_ratio_warning` 同源
（`PROSE_*` 常量都照抄了），但**多了一步"先滤掉标题行 / 图片行"的预处理** ——
于是 `total` 变小、`ratio` 被抬高，把**边界壳页**判成了可用。

实测复现（同一样本、两个脚本判定相反）：

| 样本 | `web_to_md` | 量尺（修前） |
|---|---|---|
| chooseauto | 壳页（**22% prose / 3 段**，阈值 30%）| **可用**（错）|
| 比亚迪官网 | 壳页（0%）| 壳页 |

### 代价

日志报「够了！**4 篇**可用，净正文 21,795 字符」⇒ 模型据此**提前收手、只读了 2 篇**
⇒ 最终 `文本.md` 仅 **1,125 字符**（达成率 70%），而上一次（旧版、同主题、读 6 篇）是 **1,899 字符（116%）**。

### 修法

**口径与 `web_to_md._prose_ratio_warning` 逐字一致** —— 只去 HTML 注释，**不做任何行过滤**；
另把壳页行的显示从 `0` 改为**真实净正文**（边界案例一看就懂）。
复验：chooseauto →/ 比亚迪官网 →/ 真文章 nra →（2,787），**既对齐又没矫枉过正**。

### 教训

**复用既有判据时，"常量抄对了"远远不够 —— 输入口径也必须逐字一致。**
我复制的常量是对的、函数体也照抄了，**唯独多了一步预处理**，就足以让 22% 的样本翻面。
⇒ **口径类复用：要么直接 import 那个函数，要么原地逐行对照到"输入完全相同"。**

### 补记（2026-10-15）：另一种「不同源」—— 存盘追加的 meta 头

上面那轮修的是「**在正文里多滤了几行**」；2026-10-15 又踩到同构问题的反方向：
**两边输入差在「文件头」，不在「正文」**。

`web_to_md.py` 存盘时会追加 `# {标题}` 与 `> {描述}` 两行（页面 meta，**不是正文**），
而它的 `_prose_ratio_warning` 判的是**追加之前**的 `markdown_text`；
`check_research_volume.py` 读的是**追加之后**的存盘文件 ⇒ `total` 被这两行撑大、`ratio` 被压低。

实测（同一篇真文章，d1ev《8月终端车市TOP20》）：

| 判定输入 | total | ratio | 结论 |
|---|---|---|---|
| 抓取时（追加前）| 3,119 | **30.20%** | ✅ 放行 |
| 存盘后（追加后，check 所见）| 3,244 | **29.04%** | ❌ 判壳 |

**只差 0.96 个点跨过 30% 阈值** ⇒ 该篇、连同另一篇正文 858 字的真文章（新华网）
双双被判壳，`check_research_volume` 报「可用 0 篇」⇒ 模型据此**终止**
（`SKILL_GOAL_BLOCKED`）—— 而 6 条必应词 / 3 个栏目页 / 1 次 360 探针的预算**确实已用尽**、
无法再补，整轮取材白白报废。

**修法（三条）**：① `check_research_volume.py` 加 `strip_stored_meta()`，**只剥注释头之后
紧跟的那两行**，让两边输入真正相同；② `PROSE_CHARS_MAX` 由 `1000` 下调到 `800`
（**两处同改**）；③ 汇总行的「净正文合计」只累加**可用篇** ⇒ 0 篇时显示 `0 字符`，
容易被读成「全是空的」⇒ 补印「全部文件合计 N 字符」。

⚠️ **与上一条的边界（关键）**：上一条禁的是「在**正文里**挑行丢掉」（会抬高 ratio、
把壳页误放行）；这一条剥的是「**页面 meta，不在正文里**」。
判据 = **剥掉的那行是不是由爬虫自己追加的** —— 是 ⇒ 剥（还原抓取口径）；否 ⇒ **一个都不许动**。

## 关系信息在「落盘」这一步被丢掉 —— 组件用不上，不是模型不会挑（2026-10-14 查明）

### 现象

设计侧已造了 24 类组件（C1~C10 / **R1~R6** / G1~G5 / L1~L3），契约 ②册 §4.8 也给足了
三张路由判据表；但真实产物里 **R1~R6 零引用**（2026-10-12 审计），内容页反复是
「左文右图 + 白底卡 + 斑马纹表」那一套。

### 根因：不是选型能力不够，是**判据要的输入从来没被生产过**

三张路由判据表（②册 §4.8）与 ③册 §5.0 速查表的「手上的内容」一列，
**输入全部是「这块内容是什么逻辑关系」**（并列 / 构成 / 对比 / 递进 / 时序 / 分层）。
而事实提取端实际交付的是：

| 层 | 实际形态 | 带关系吗 |
|---|---|---|
| `_research/facts.txt` | `F001 \| claim \| 来源 \| URL \| 日期` | ❌ 五个字段全是溯源信息 |
| `_web_text_facts.json` | 同上 ＋ schema / topic / mode | ❌ |
| `文本.md` 网络段 | `- claim` **逐条平铺** | ❌ 连来源标题都不带 |

⇒ Step 1 拿到的是一袋**互不相干的断言**，只能退回最弱的默认「并列」——
于是 `R1`（要"各项各有占比"）、`R3`（要"恰好两项对照"）、`R6`（要"递进"）、
`L1~L3`（要"时间 / 发展叙事"）**全部触发不了**。

### 最要命的是「时间错配」

关系**只在模型刚读完原文那一刻判得出来**。而 §0d E 紧接着就**整目录删掉
`_research/`**（全部抓取件在内）⇒ 到 Step 1 选骨架时，**连反推关系的原料都没了**。
不是"模型不够聪明"，是**信息在需要它之前就被销毁了**。

### 修法（2026-10-14）：把关系提取出来并**落盘**

`facts.txt` 新增 `#GROUP <组id> | <关系> | <组标题>` 指令行（管辖到下一个
`#GROUP` 为止）⇒ 渲染成 `文本.md` 网络段里的 `### [G1] 构成 · …` ⇒ Step 1 直接读。
六个关系值**严格取自契约已有出口**，不发明概念：

| 关系 | 出口 |
|---|---|
| 并列 | §5.2 多栏并列 / §5.6 卡片矩阵 |
| 构成 | R1 进度条 / §5.9 不等宽主分区 |
| 对比 | R3 VS 对比卡 / §5.18 双图对开 |
| 递进 | R6 递增柱 / L2 阶梯轴 / §5.15 阶梯 |
| 时序 | §5.3 流程链 / L1 中轴交替 / L3 阶段色带 |
| 分层 | §5.10 编号条目列 / §5.19 环形放射 |

⚙️ 配套三处（缺一不可）：

1. `emit_facts.parse_facts` 捕获 `#GROUP`；**无 `#GROUP` 时输出与改动前逐字节一致**
   （实测比过 md 与 json）—— 向后兼容不是口头承诺；
2. `verify_extraction.body_only` 新增 `GROUP_HEAD_RE` 把组标题行**剥掉** —— 它是
   元信息、不是素材，留着会让正文体量虚高、把「素材偏少」的告警压掉；
3. 落盘打一行 `→ 关系覆盖：N 组（构成×1 / 时序×1 …）`；**显示 0 组 = 漏标**，当场可见。

### 教训

**"下游判据要用到的东西"，必须在上游就被当作交付物产出来。**
路由判据在契约里写得再漂亮，只要上游不生产它要的输入，就是死条文 ——
`R1~R6 零引用`不是文档问题，是**数据流缺了一环**。
⇒ 排查「某个能力从来没用上」时，先问一句：**它依赖的输入，前面某一步真的产出了吗？**


### 子步编号重排 ＋ 新增「§0c 统一结构化」（2026-10-14）

**问题**：取材有两条路（**本地素材** / **联网取材**），但**只有联网那条产出逻辑关系标注**。
走本地素材时 Step 1 只能退到默认「并列」⇒ 关系驱动的组件（R1 / R2 / R3 / R6 / L1~L3）
与骨架（§5.3 / §5.9 / §5.10 / §5.15 / §5.19）**系统性用不上**。

⚠️ 别把病根认成「两条路浓度不同」—— **浓度不同不是 bug**：网页原文该浓缩（几万字、
混着导航）；调用方给的正文**同样是待加工原料**，要**提纯**成要点清单（原文另存留档）。
真正缺的是**出口形态**：两边都得给「这块内容是什么关系」，本地这路还要多给「每张图是什么」。

**修法（分两次落地，最终态见下）**：

1. **新增「§0c 统一结构化」一步，把本地素材并入与联网取材同一套流水线** ——
   跑 `emit_facts.py --local --sync-text` 出 `[L…]` 本地段（**提纯 + 标关系**），
   再补「内容：」并挪进图片登记段（**2026-10-15 起：内嵌图据原文图注即可、不必逐张看图**）。
   `[L…]`（本地）与 `[G…]`（网络）**命名空间并列不冲突、语法同形** ⇒ 下游一套正则。
   🔑 **本地不做溯源**：不产 `_web_text_facts.json`、facts 末字段可空（网络段强制带 URL 才是红线）；
   图片也不写来源。差异只有两点：**无 URL** ＋ **多一步图片含义**。
2. **子步编号重排 ＋ `§0c`/`§0d` 对调**（顺带把突兀的字母 `r` 收进序列）：
   原始 → 终态 = `§0r→§0d`（联网取材）｜**新增 §0c**（统一结构化）｜`§0c→§0e`｜`§0d→§0f`｜
   `§0e→§0g`｜`§0f→§0h`｜`§0g→§0i`；`前置 / §0a / §0b` 不变。
   🔑 **结构化排在联网取材之前**（`b → c → d`），因为「**量体量**」必须**在提纯之后**才准
   （拿原文量 ⇒ 提纯缩水后没人再量 ⇒ **静默漏判**）。
   重排共改 **303 处引用（232 处 `§` ＋ 71 处裸编号）／ 18 个文件**；后续对调另改约 130 处／16 文件。
   🔑 **只改引用、不改任何判据**。⚠️ 当时加在 `step_0_extract.md` 顶部的「🔄 子步编号重排」对照块，**当日已删除** —— 用户判定：没必要，且会让新读者照旧号理解文档。
   🔴 **本类改动的高危坑**：机械全库替换 `§0c↔§0d` 会**误伤「旧→新」映射行本身**
   （那一行的 `§0c`/`§0d` 指**旧号**）⇒ 对调**必须留映射表、替换后逐行回读**。
3. `verify_extraction` 把组标题行剥离从 `\[G\d+\]` 放宽到 `\[(?:G|L)\d+\]`（`GROUP_HEAD_RE`），
   否则**本地段新加的 `### [L…]` 标注行会被算进正文体量**（体量虚高 ⇒ 把「素材偏少」的告警压掉）；
   同脚本新增 **①-d 检查**（`LOCAL_SECTION_MARK` + `LOCAL_HEAD_RE`）：有本地段却**零 `[Ln]`** ⇒ 告警不阻断。

**三条红线（犯了都不报错）**：① **不改原文** —— 提纯结果写新清单 `_local_facts.txt`，
`文本.md` 的替换**由脚本做**（原文已在 `_local_source.md` 留档）；
② 🔴 **绝不插 `---`** —— `check_materials.py:97` 用 `'\n\n---\n\n'` 数**来源段**，
插一条水平线**凭空多出一个假来源段**；③ **图必须在落盘（③）前挪进登记段**
（`## 附加图片` / `## 联网补充图片`）—— §0e 复验「占位符数 = 图片数」，
正文里残一个 `[[image_NNN]]` 就会被整段替换掉 ⇒ 当场失败。

**教训（与上一节同源）**：判断「某个能力为什么从来用不上」时，先看它依赖的输入
**在整条链上有没有人产出**；**两条并行路径产出形态不一致**是典型的结构性断点 ——
判据写得再准，上游只喂一半，就等于没有。

**另一条工程教训**：`Path.read_text()` 会把 `\r\n` 归一成 `\n`，回写就把 CRLF 洗成 LF。
**本库有 CRLF 与 LF 混存**（`emit_facts.py` 是 LF，其余绝大多数是 CRLF）⇒
改文件**一律走 bytes 级读写**（`read_bytes().decode()` → `write_bytes(...encode())`），
别用 `read_text()`；改完必须回查一次行尾计数。


### 顶层步骤改名：「Step 0: 素材提取」→「素材准备」（2026-10-14）

**问题**：入口步骤顶着编号 `Step 0`，与它的性质不符 —— 它**不是流水线的第 0 环，是开工前的准备**。

**改法**：**只改称呼** —— 文件名 / 脚本名 / 子步编号 / 任何判据，一个都没动。
