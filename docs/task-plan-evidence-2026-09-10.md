# 任务命名与执行计划证据约束

当前产品定位是 Agent 驱动的任务编排：一个任务、一个独立沙箱，按计划顺序协调所选 Skill。固定任务阶段是生命周期；业务步骤由执行计划描述。当前没有通用 DAG 调度、条件分支、任务内并发或子 Agent。

## 本次变更

- 页面统一使用“任务”“执行能力”；保留内部 workflow 类型、路由和 API，兼容现有客户端。
- 同一 step id 的状态更新若省略 depends_on、input_refs、output_refs 或 skill_index，保留已有约定。明确重规划仍可传新数组（包括空数组）；删除步骤时仍须满足完整依赖检查。
- 已声明的输入必须存在，已完成步骤的输出必须存在。平台继续记录文件摘要，文件变化使相关步骤及其后继失效。
- 最终验证步骤只有在当前需求和工作区的 record_validation 通过后才能完成，不能跳过。新增需求必须重新验证。
- 验证完成后再次执行工作区写操作（包括已执行但失败的操作），最终验证退回 pending，避免界面保留过期的完成状态。
- 引导 Agent 在阶段完成、下一阶段开始前更新计划，并声明文件输入输出和可测量的验收条件。
- 修复无限轮数路径缺少 itertools 导入的问题；不改变轮数或超时默认值。

## 能力边界

文件存在与摘要一致不证明内容语义正确。普通步骤的完成说明仍由 Agent 提交；最终内容检查通过既有 run_verifier / record_validation 协议执行，验证程序可能由 Agent 编写。此次没有增加通用逐步骤语义验证器，也没有将任意命令绑定到步骤的文件权限范围。

可恢复的工具错误仍由 Agent 在当前沙箱中修复；不增加沙箱销毁后的断点恢复或跨任务复用。不限总时长、首响应和流停滞超时设置保持原样。

## 验证

计划策略、编排集成、Worker 协议、模型工具和 Agent 内核共 98 项测试通过；前端 TypeScript 检查和生产构建通过。新增用例覆盖漏传字段、缺失文件、最终验证提前完成/跳过、需求变更以及失败写操作后的验证失效。
