# SkillGo 业务能力审计与优化路线图

> 日期：2026-08-04
> 当前判断：已具备可验证的纵向业务闭环，属于“可供内部试用的 Alpha”，尚不是可正式承诺 SLA 的多人工作流平台。

## 2026-08-12 产品模型统一进展

第一批收敛已开始实施：

- 工作台首页保持聚焦输入框，不恢复占据大面积的最近记录列表；
- 顶部新增轻量历史对话入口，支持搜索、打开、重命名和删除；
- 普通用户导航取消独立“运行记录”，统一使用“任务”心智；
- 任务中心同时展示对话发起的 Skill 沙箱任务，以及网页/API 的轻量服务调用；
- 旧 `/app/runs` 地址保留兼容跳转，既有链接不会失效；
- 底层 `Run` 继续保留为审计与开发者对象，但不再要求普通用户理解两套执行概念。

下一批将聚焦结果表达与文件体验：Markdown/结构化结果渲染、多附件、历史文件复用，以及任务失败后的可操作恢复建议。

## 1. 产品结论

SkillGo 的核心不应被定义成“一个运行 ZIP 的沙箱”，而应被定义成：

> 将可版本化、可审核、可对话运行的 Skill，发布为人可以使用、系统也可以调用的工作流能力。

同一个 Skill 应有两个入口，但共用同一个版本、权限和 Run 记录：

1. **给人使用：Agent 对话入口**。用户发送自然语言、文件和补充信息，默认看到易读结果。
2. **给系统使用：API 入口**。调用方提交结构化 JSON，得到稳定、可校验、可追踪的结构化结果。

因此，“网页不显示 JSON”与“API 使用 JSON”并不冲突。网页负责把结构化结果渲染成人能读懂的内容，API 继续维护严格契约。

## 2. 当前能力评估

| 能力 | 当前状态 | 判断 |
|---|---|---|
| 账号与三级角色 | 登录、注册、超级管理员、管理员、普通用户和服务端权限校验已存在 | 基础可用 |
| Skill Registry | 创建、ZIP 上传、结构校验、版本哈希、版本状态、删除已存在 | 基础可用 |
| 社区 | 公开搜索、分类、详情、下载、收藏、审核已存在 | 只有最小闭环 |
| Agent 对话 | 自然语言、多会话、重命名、历史上下文、并发锁已存在 | 可试用，结果表达需升级 |
| 会话文件 | 用户级和会话级归属校验；文本、DOCX、XLSX 可提取；其他格式可存储 | 基础可用，能力边界需说清 |
| Run | 控制台和 API 统一留存输入、输出、模型、耗时与错误 | 基础可用，缺少详情和步骤 |
| API Endpoint | 已发布指令型 Skill 可部署、生成密钥、同步调用、停用和轮换密钥 | PoC 可用，不宜承诺生产级能力 |
| 管理后台 | 用户停用、角色修改、版本批准/驳回、系统摘要已存在 | 审核信息不足，治理能力偏弱 |
| 数据持久化 | PostgreSQL 与文件卷已持久化，重启不会清空业务数据 | 本机部署可用 |
| 代码与工具执行 | 代码型 Skill 被阻止直接执行，沙箱仅有 PoC | 决策正确，等待 Linux |

本次审计中，17 个后端自动化测试全部通过；本机数据库、API 和网页服务健康，API 文档可访问。这说明基础链路不是纯页面演示，但仍有明显的产品闭环缺口。

## 3. 主要业务问题

### 3.1 导航与“返回首页”语义混乱

当前工作台侧栏使用同一个品牌 Logo，点击会回到公开 Skill 市场。对工作中的用户而言，Logo 通常代表“回到工作台概览”，突然离开工作台会造成上下文切换。

建议：

- 公开区域的 Logo 返回 Skill 市场；
- 工作台内的 Logo 返回工作台概览 `/app`；
- 侧栏新增明确的“发现 Skill”入口进入公开市场；
- Skill 详情、版本管理、Agent 对话使用一致的面包屑；
- “返回版本”改为“返回 Skill 详情”，避免把数据结构术语当成用户语言；
- 登录和注册页提供清晰的“返回 Skill 市场”。

### 3.2 首页和功能文案存在超前承诺

当前页面提到了 SSE 和 Webhook，但代码只实现了同步 Endpoint。超前文案会直接降低用户信任。

建议在功能未完成前，将首页表述改为“同步 API 与可追踪 Run”；SSE、异步任务和 Webhook 进入路线图，不作为现有能力宣传。

### 3.3 对话结果仍可能退化成原始 JSON

当前会优先提取 `message/answer/result/summary/content/text/joke` 等文本字段；如果输出稍复杂，就会直接显示完整 JSON。这对普通用户不友好。

建议建立统一的结果渲染层：

- 单段文字显示为正常对话；
- 列表显示为要点或结果卡片；
- 键值对象显示为字段卡片或表格；
- 文件显示为可下载产物；
- 原始 JSON 收进“查看原始数据”，默认折叠；
- 结构化输出仍原样保存到 Run，不能为了好看丢失字段。

### 3.4 API 能调用，但只是同步 PoC

当前调用链路真实存在：Endpoint 锁定已发布版本、API Key 只显示一次且仅保存哈希、输入和输出按 Schema 校验、执行记录进入 Run。

目前的限制：

- 请求会一直等待模型返回，没有队列；
- 没有异步创建任务和状态查询；
- 没有 SSE、Webhook、取消、重试和幂等键；
- 没有限流、配额、调用统计和独立开发者日志；
- Endpoint 页面没有在线调试、Schema 表单或 curl/Python/JavaScript 示例；
- 通用 OpenAPI 文档无法充分表达每一个 Endpoint 的真实输入 Schema；
- API 调用失败虽然产生 Run ID，但外部调用方还没有使用 Endpoint Key 查询该 Run 的完整通道。

结论：现在可用于内网同步短任务验证；经过“开发者控制台 + 同步 API 加固”后可用于小范围集成；异步和高并发需要队列/Worker 后再承诺。

### 3.5 社区还不是完整的分享与复用市场

目前更接近“公开 Skill 展示与 ZIP 下载”。尚缺：

- 收藏取消和“我的收藏”；
- 安装到个人空间或一键派生；
- 下载/安装统计；
- Skill 元数据编辑；
- unlisted/internal 的真实访问入口；
- 版本更新说明、作者页、举报入口；
- 搜索排序、分页和更多筛选；
- 已发布版本的弃用/下架，而不是只能删除整个 Skill。

### 3.6 管理员无法高质量审核

审核卡片目前只突出版本号、类型、哈希和权限项数量，管理员缺少 Skill 名称、作者、说明、完整权限、Manifest、版本内容和包下载等关键证据。批准/驳回还使用浏览器原生输入框。

这会让“审核”变成形式操作，应优先升级为审核详情页和标准确认对话框，并补充审计日志入口。

### 3.7 工作台存在“有数据但不能继续操作”的页面

- 概览指标不可点击；
- Run 列表没有 Run 详情，无法查看完整输入、输出和错误；
- Endpoint 列表不能在线测试，也没有调用示例；
- “连接与密钥”仍是占位页，却以正式功能出现在主导航；
- 部分可见性和状态直接显示英文枚举；
- 多处使用浏览器原生 `prompt/confirm`，视觉与操作反馈不一致。

## 4. 分阶段优化方案

### 阶段 A：修复用户旅程与产品可信度（第一批）

> 交付状态：已于 2026-08-04 完成。本机版本已更新，Linux 相关工作未启动。

目标：用户在任何页面都知道“我在哪里、下一步做什么、怎样回去”。

范围：

1. 重构公开市场与工作台的导航归属；
2. 增加工作台“发现 Skill”入口和统一面包屑；
3. 修正“返回版本”等不自然文案；
4. 让概览指标和最近运行可以继续点击；
5. 隐藏或明确标注未开放模块；
6. 统一中文状态、空状态、错误反馈和确认框；
7. 删除首页对 SSE/Webhook 的超前承诺；
8. 明确文件格式哪些“可读取”、哪些“仅存储”。

验收：从市场、上传、版本、运行、API、审核任意页面都能用一到两步回到合理上级，不依赖浏览器后退。

### 阶段 B：升级 Agent 对话与 Run 可读性（第二批）

目标：普通用户只关注任务和结果，不需要理解 JSON、Schema 或 Run 数据结构。

范围：

1. 新增统一结构化结果渲染器，原始 JSON 默认折叠；
2. 首轮消息自动生成有意义的会话名，可继续手动修改；
3. 增加 Run 详情页，展示状态、输入、结果、错误、耗时、模型和关联会话；
4. 对话结果与 Run 详情互相跳转；
5. 优化文件区：预览可读内容、标明读取状态、区分输入文件与产物；
6. 长任务先改善等待态和超时提示，后续再接流式输出。

验收：复杂对象不会直接以整块 JSON 打断对话；用户仍可按需查看和复制原始数据。

### 阶段 C：补齐社区与审核闭环（第三批）

目标：Skill 不只是被展示，而是能被可信地发现、复用、更新和治理。

范围：

1. 收藏切换与“我的收藏”；
2. 下载记录、安装到个人空间和派生副本；
3. Skill 基本信息编辑、版本更新说明、弃用与下架；
4. unlisted/internal 的真实访问规则；
5. 审核详情页、完整权限对比、包下载和审批理由；
6. 管理操作确认与审计日志页面；
7. 搜索分页、排序、标签与作者信息。

### 阶段 D：把同步 API 做成可交付能力（第四批）

目标：让开发者不依赖阅读后端源码即可完成一次可靠集成。

范围：

1. Endpoint 详情与在线调试台；
2. 基于真实 Schema 自动生成表单和请求示例；
3. 一键复制 curl、Python 和 JavaScript 示例；
4. 统一响应信封、错误码、请求 ID 和 Run ID；
5. Endpoint Key 的名称、过期、最后使用时间、轮换和撤销；
6. 基础限流、配额、超时与调用统计；
7. `Idempotency-Key` 防止客户端重试产生重复任务；
8. 固定对外 API 版本并补充契约测试。

同步 API 建议使用稳定资源语义：

```http
POST /api/v1/endpoints/{slug}/runs
X-SkillGo-Key: skg_...
Idempotency-Key: optional-unique-key
Content-Type: application/json

{
  "input": {}
}
```

### 阶段 E：异步运行与 Linux 执行面（服务器到位后）

目标：支持长任务、并发、工具调用和代码型 Skill。

范围：

1. API 与 Worker 分离，增加任务队列；
2. 异步 Run 查询、取消、重试、超时；
3. SSE 事件流与签名 Webhook；
4. 对象存储中的输入文件、日志和产物；
5. Tool Gateway，按用户、会话和权限发放临时能力；
6. 代码型 Skill 使用一次性 Linux 沙箱、非 root、默认断网和资源限制；
7. 数据库迁移、备份恢复、监控、TLS 和灾难恢复。

沙箱只保护代码与高风险工具执行，不应成为普通对话和指令型 Skill 的产品中心。

## 5. 推荐实施顺序

后续严格按下面批次逐步交付，每一批都独立构建、测试和验收：

1. **第一批：导航、文案、可操作性和真实能力边界**；
2. **第二批：对话结果渲染和 Run 详情**；
3. **第三批：Endpoint 开发者控制台与同步 API 加固**；
4. **第四批：社区复用与管理员审核**；
5. **第五批：Linux 队列、工具网关与沙箱执行器**。

暂不投入：收费市场、可视化拖拽编排、Kubernetes、多地域、复杂组织体系和任意第三方工具生态。这些会稀释当前最重要的“上传—运行—调用—追踪”闭环。

下一轮从以下小步开始：

本批实际完成：工作台与市场导航拆分、工作台面包屑、Agent 返回路径、可点击概览指标、真实平均耗时口径、规划模块降级、首页 API 文案校正、状态与可见性中文化、文件读取能力提示、管理员审核对话框。
